# MVP 다음 단계. 원자료 기반 중요도 판정

## 문서 상태

- 버전: v0.1
- 상태: 계획. **MVP에는 포함하지 않는다**
- 선행 조건: [MVP 범위](mvp-scope.md)의 Must가 동작하고 12장 합격선을 판정한 뒤에 시작한다
- 관련 문서: [MVP 범위 6.5.1 중요도 지정](mvp-scope.md), [MVP 범위 8.4](mvp-scope.md), [제품 방향](product-direction.md), [ADR 0001](../adr/0001-tech-stack.md)

이 문서는 MVP 이후 단계의 설계를 미리 고정해두기 위한 것이다. 지금 구현하지 않는다. 다만 MVP 설계에서 **막아두지 말아야 할 것**이 무엇인지 알기 위해 먼저 쓴다.

## 1. 왜 하는가

MVP의 중요도 지정은 두 가지로 동작한다. 사용자가 직접 끌어 놓거나, 하위 덱 이름의 키워드로 추측하거나. 둘 다 한계가 분명하다.

- 수동은 사용자가 이미 아는 것만 반영한다.
- 키워드 추측은 덱 이름이 잘 지어진 경우에만 맞는다.

정작 중요도의 진짜 근거는 **학습 자료 안에** 있다. 인터뷰에서 사용자는 이렇게 진술했다.

> 무조건 출제될 것 같은 포인트들(교수 강조, 기출 이력 有, 핵심 개념 등)이 있어서 이것들에 조금 더 집중하고 싶을 때도 많아. 보통 LLM에게 전달하는 파일에 수기로 별표가 쳐져 있거나 하이라이트, 붉은 글씨 등으로 강조를 해 놓는 경우가 많아.

즉 사용자는 **이미 자료에 중요도를 표시해두었다.** 그 표시를 앱이 읽으면 중요도를 추측할 필요가 없다.

## 2. 무엇을 만드는가

하나의 기술로 두 기능이 나온다. 이게 이 단계의 핵심 이점이다.

| 기능 | 근거 문서 |
|---|---|
| 자료의 강조 표시로 카드 중요도를 제안한다 | MVP 범위 8.4, 6.5.1의 4층 |
| 어려운 카드에서 원본 문단으로 돌아간다 | 제품 방향 `Source-linked learning` |

둘 다 **카드와 자료 구간을 연결하는 것** 하나에서 파생된다. 연결만 만들면 두 번째는 거의 공짜다.

두 번째 기능에 대한 사용자 진술이다.

> 힌트 자체보다는 너무 어려워하면 관련 해설을 원자료 기반으로 제시해서 다시 한번 짚어주는 세션이 있어도 좋을 것 같아.

## 3. 파이프라인

```text
자료 파일 등록 (PDF / PPTX)
→ 텍스트와 서식 추출          문단 단위, 위치 포함
→ 강조 신호 추출              하이라이트, 색상, 볼드, 크기, 목차 레벨
→ 문단 임베딩
→ 카드 임베딩
→ 유사도 매칭                 카드 ↔ 문단
→ 카드별 강조 점수 산출
→ 하위 덱 단위 집계
→ 중요도 제안
```

## 4. 단계 쪼개기

이 단계 안에서도 한 번에 다 하지 않는다. **B-1은 모델 없이 동작한다**는 점이 중요하다. 위험이 가장 낮은 것부터 간다.

| 단계 | 내용 | 모델 필요 | 얻는 것 |
|---|---|---|---|
| **B-1** | 자료 등록 + 강조 추출 + 수동 연결 | 없음 | "원자료로 돌아가기"가 이미 동작한다 |
| **B-2** | 임베딩 자동 매칭 + 중요도 제안 | 임베딩 (약 100~500MB) | 중요도가 근거를 갖는다 |
| **B-3** | 카드 재구성 제안 (긴 답변 쪼개기 등) | 소형 LLM (1~3GB) | MVP 범위 8.2에 해당 |

B-1만으로도 제품 가치가 있다. B-2에서 막히면 B-1에서 멈춰도 손해가 아니다.

## 5. B-1. 자료 등록과 강조 추출

### 지원 형식

| 형식 | 처리 |
|---|---|
| PDF (텍스트 레이어 있음) | 지원 |
| PPTX | 지원. OOXML zip + XML이라 표준 파싱으로 충분하다 |
| PDF (스캔 이미지만) | **범위 밖.** OCR이 필요하다 |
| 손글씨 표시 | **범위 밖.** 이미지라 OCR과 같은 문제다 |

마지막 항목은 인터뷰의 "수기로 별표"와 직접 관련이 있다. 타이핑한 `★`나 `*`는 텍스트라 읽히지만, 인쇄물에 손으로 그린 표시는 읽을 수 없다. 사용자에게 이 구분을 명시해야 한다.

### 강조 신호

| 신호 | 추출 방법 | 신뢰도 |
|---|---|---|
| PDF 하이라이트 주석 | 주석 객체를 직접 읽는다 | 높음 |
| 글자 색 (붉은 글씨 등) | 텍스트 span의 color 속성 | 높음 |
| 볼드 | 폰트 flags | 중간 |
| 글자 크기, 목차 레벨 | font size + PDF outline | 중간 |
| 타이핑된 별표 `★` `*` | 텍스트 매칭 | 중간 |
| 밑줄 주석 | 주석 객체 | 높음 |

신호마다 가중치를 둔다. 하이라이트와 색상은 사용자가 의도적으로 남긴 것이라 가중치가 높고, 볼드와 크기는 문서 원본의 서식일 수 있어 낮다.

### 라이브러리

ADR 0001에서 Rust(Tauri)로 결정했으므로 Rust 크레이트를 먼저 본다.

| 후보 | 주의 |
|---|---|
| `lopdf` | 순수 Rust. 주석과 서식 접근이 저수준이라 손이 많이 간다 |
| `pdfium-render` | 기능이 가장 풍부하다. pdfium 바이너리를 동봉해야 한다 |
| `pdf-extract` 등 | 텍스트만 뽑는다. 서식과 주석이 없으면 이 단계에는 쓸모없다 |

**텍스트만 뽑는 라이브러리는 후보가 아니다.** 필요한 건 하이라이트 주석, 글자 색, 볼드다. 후보를 고를 때 이 세 가지 접근 가능 여부를 먼저 확인한다.

라이선스도 확인한다. 배포하는 데스크톱 앱이므로 AGPL 라이브러리를 링크하면 앱 전체에 의무가 전파될 수 있다. Python의 PyMuPDF가 기능은 가장 좋지만 AGPL이라 이 이유로도 후보에서 빠진다.

### 완료 조건

- 자료를 등록하면 강조된 구간이 목록으로 보인다.
- 카드에서 연결한 자료 구간으로 이동할 수 있다.
- 자료를 등록하지 않아도 앱이 정상 동작한다.

## 6. B-2. 임베딩 매칭과 중요도 제안

### 모델 요건

| 항목 | 요건 |
|---|---|
| 종류 | 문장 임베딩 |
| 언어 | **다국어 필수.** 한국어 강의 자료를 다룬다 |
| 크기 | 100~500MB |
| 실행 | CPU에서 실용적인 속도가 나와야 한다 |
| 후보 | `multilingual-e5-small`, `bge-m3`, `paraphrase-multilingual-MiniLM` 계열 |
| 런타임 | `ort` 크레이트 (ONNX Runtime의 Rust 바인딩) |

### 계산량

카드 수천 장과 문단 수천 개면 임베딩은 각각 한 번씩만 계산하고 저장한다. 매칭은 행렬곱 한 번이다. 이 규모에서는 부담이 없다.

임베딩은 카드나 자료가 바뀔 때만 다시 계산한다.

### 매칭 임계값

유사도가 낮으면 **연결하지 않고 비워둔다.** 억지로 매칭하면 잘못된 근거가 만들어지고, 그건 근거가 없는 것보다 나쁘다.

임계값은 실측으로 정한다. 6절 검증 참고.

### 중요도 산출

```text
카드 점수     = 매칭된 문단들의 강조 점수 가중합
하위 덱 점수  = 소속 카드 점수의 분포 (중앙값과 상위 비율)
제안          = 상위 구간 하위 덱 → 핵심, 하위 구간 → 보충
```

절대 점수가 아니라 **덱 안에서의 상대 순위**로 판단한다. 자료마다 강조 밀도가 다르기 때문이다.

### 설명 가능성

제안에는 반드시 근거 한 줄이 붙는다.

```text
3장 요약  →  핵심으로 제안
            이 덱의 카드 12장이 하이라이트된 구간과 연결됨
```

MVP 범위 6.5.1의 조건을 그대로 따른다.

- 제안 없이도 중요도 지정이 완결된다.
- 사용자가 확정한 값을 제안이 덮어쓰지 않는다.
- 적용 전에 확인하고 수정할 수 있다.
- 근거를 한 줄로 제시한다.

### 모델 배포 방식

| 방식 | 장단 |
|---|---|
| 설치 파일에 번들 | 오프라인 첫 실행 가능. 설치 파일이 100~500MB 커진다 |
| **첫 사용 시 다운로드** | 설치 파일이 작다. 자료 분석을 안 쓰는 사용자는 받지 않아도 된다 |

**다운로드를 추천한다.** 이 기능은 선택 기능이고, 쓰지 않는 사용자에게 비용을 지울 이유가 없다.

## 7. 검증

구현 전에 두 가지를 실측한다. 둘 다 본인 강의 자료로 할 수 있다.

**검증 1. 강조 추출이 실제로 되는가**

본인이 하이라이트와 색상 표시를 해둔 강의 PDF를 하나 골라서, 표시한 구간이 전부 추출되는지 센다. 놓친 것과 잘못 잡은 것을 세면 그대로 신호별 가중치의 근거가 된다.

**검증 2. 매칭이 쓸만한가**

카드 20장을 고르고 손으로 정답 문단을 지정한다. 임베딩 매칭 결과와 비교한다.

- 상위 1개가 정답인 비율
- 상위 3개 안에 정답이 있는 비율
- 정답이 없는 카드를 "연결 없음"으로 올바르게 판정한 비율

세 번째가 가장 중요하다. 잘못된 연결은 잘못된 중요도를 만들고, 사용자는 그걸 믿고 학습 순서를 정한다.

기준선은 임의로 정하지 않는다. 실측 후 "이 정도면 쓸만한가"를 직접 보고 판단한다.

## 8. MVP에서 미리 열어둘 것

이 단계를 위해 MVP에서 지금 해둬야 하는 일은 많지 않다. **두 개뿐이다.**

| 항목 | 이유 |
|---|---|
| 중요도에 `출처` 필드 (`수동` / `규칙` / `자료`) | 이미 MVP 범위 6.5.1에 넣었다. 없으면 나중에 사용자 설정을 덮어쓴다 |
| 카드 ↔ 자료 구간 연결을 담을 자리 | 테이블 하나를 추가할 수 있게 스키마가 열려 있으면 된다 |

두 번째는 MVP에서 **테이블을 만들 필요도 없다.** 카드에 외래 키를 미리 박아두지 말고, 나중에 연결 테이블을 따로 추가하면 된다. 지금 할 일은 "그게 가능한 구조인지" 확인하는 것뿐이다.

그 외에는 미리 준비할 것이 없다. 자료 파싱도, 모델도, 화면도 전부 이 단계에서 시작한다.

## 9. 이 계획의 전제

| 전제 | 깨지면 |
|---|---|
| 데스크톱 앱이다 | 모델 파일과 자료 파일 관리가 어려워진다. ADR 0001 3장을 다시 본다 |
| 사용자가 자료에 강조 표시를 해둔다 | 추출할 신호가 없다. 목차와 글자 크기만으로는 약하다 |
| 자료에 텍스트 레이어가 있다 | 스캔본뿐이면 OCR이 선행되어야 하고, 그건 별도 과제다 |

두 번째 전제는 지금 한 명의 인터뷰에만 근거한다. 다른 사용자도 그렇게 하는지는 확인되지 않았다.
