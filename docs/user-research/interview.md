# Neo-Anki 요구사항 도출 대화 원문

## 문서 성격

작성자가 **사용자 입장에서 자신이 원하는 것을 끌어내기 위해** LLM과 나눈 대화다. Neo-Anki의 모든 기획 문서가 여기서 출발했다.

| 항목 | 내용 |
|---|---|
| 종류 | 요구사항 도출 대화 로그 |
| 일자 | 2026년 7월 30일 |
| 참여 | 작성자 ↔ LLM |
| 후속 정제본 | [Anki 장기 사용자 인터뷰](anki-power-user-interview.md), [제품 방향](../product/product-direction.md) |

## 이 대화의 구성

| Part | 성격 | 읽는 법 |
|---|---|---|
| Part 1 | LLM이 독립 SRS 앱 방향을 제안 | 제안을 작성자가 검토한 구간. 제안 내용 자체는 작성자의 결론이 아니다 |
| Part 2 | 작성자가 Anki 호환성을 요구 → LLM이 설계 전환 | **작성자의 요구가 방향을 바꾼 지점** |
| Part 3 | LLM이 기획 초안 정리 | Part 1~2의 합의를 문서화한 것 |
| Part 4 | 작성자가 질문에 직접 답변 | **작성자의 직접 발화** |

Part 1~3에서 작성자의 발화는 `> **작성자**` 인용으로 표시했다. 나머지는 LLM 출력이다.

> **인용할 때 주의.** Part 1~3의 기술 제안(스택, 데이터 모델, 스케줄러 수식, 로드맵)은 **검토 대상으로 제시된 선택지**이지 확정된 결정이 아니다. 확정된 결정은 [MVP 범위](../product/mvp-scope.md)와 [ADR 0001](../adr/0001-tech-stack.md)에만 있다.
>
> 실제로 Part 1의 `웹앱 우선 + 직접 만든 SM-2` 제안은 이후 확정된 `SRS-preserving`(검증된 SRS 재사용) 원칙과 충돌하고, Part 1.8의 `Card(front, back)` 모델은 Part 2에서 스스로 뒤집힌다. 채택되지 않은 제안이 섞여 있으니 이 문서를 근거로 삼을 때는 후속 문서와 대조할 것.

## 정리하면서 한 일

- 채팅 복붙 서식을 마크다운 구조로 변환했다. 표, 코드 블록, 제목 계층
- 화자와 턴 경계를 표시했다
- `9s 동안 생각함`, `메모리 업데이트됨` 같은 UI 잔여물을 제거했다
- 6라운드 질문 목록이 두 번 반복된 부분을 답변이 있는 쪽으로 병합했다
- 채택되지 않고 뒤집힌 제안에 `⚠️` 표시를 달았다

**내용은 삭제하지 않았다.**

# Part 1. 독립 SRS 앱 방향

> _이 앞의 대화는 로그에 남아있지 않다. `1안 = 완전 독립 앱` 방향으로 정리된 상태에서 시작한다._

## 1.1 목적 재정의

1안, 완전 독립 앱으로 가려는 거면 목적을 이렇게 잡는 게 좋다.

> "Anki를 이기겠다"가 아니라,
> **내가 매일 쓰고 싶은 더 단순하고 편한 SRS 앱을 만든다.**

사이드프로젝트로는 오히려 1안이 제일 좋을 수 있다. 이유는 간단하다. Anki 호환성, `.apkg` 파싱, 기존 스케줄러 완전 재현, 애드온 생태계 대응 같은 복잡한 문제를 처음부터 안 가져가도 되니까. 대신 직접 학습 경험, 데이터 구조, 복습 플로우, 동기화 구조를 설계했다는 점을 보여줄 수 있다.

## 1.2 핵심 포지션

> Neo-Anki는 LLM API 없이 작동하는 local-first 개인 암기 학습 앱이다.
> 사용자는 카드를 직접 만들고, 앱은 복습 흐름, 카드 정리, 오답 관리, 학습 지속성을 편하게 만든다.
> 서버는 카드 생성이나 AI 처리가 아니라, 여러 기기 간 카드와 복습 기록을 동기화하는 용도로만 사용한다.

이러면 "AI 서비스"가 아니라 **학습 생산성 도구**가 된다.

AX는 이렇게 정의하면 좋다.

> **AX, Anki Experience**란 카드 생성부터 복습, 오답 관리, 카드 수정, 동기화까지 이어지는 전체 암기 경험을 덜 피곤하게 만드는 것.

## 1.3 사이드프로젝트로 좋은 이유

단순 CRUD 앱이 아니라 다음 요소가 다 들어간다.

| 요소 | 보여줄 수 있는 역량 |
|---|---|
| 카드, 덱, 태그 관리 | 데이터 모델링 |
| SRS 복습 알고리즘 | 알고리즘 및 상태 관리 |
| 오답 로그, 응답 시간 기록 | 사용자 행동 데이터 설계 |
| local-first 저장 | 오프라인 앱 구조 |
| 서버 동기화 | 백엔드, 인증, 충돌 해결 |
| 카드 품질 관리 | 제품 기획, UX 사고 |
| 통계 대시보드 | 데이터 시각화 |
| 모바일 친화 UI | 실제 사용성 중심 개발 |

특히 "LLM 없이"라는 점도 나쁘지 않다. 요즘 너무 많은 프로젝트가 "PDF 넣으면 AI가 카드 만들어줌"으로 가는데, 이건 API 의존성이 강하고 비슷비슷하다. 오히려 **매일 쓰는 학습 루틴 자체를 개선하는 앱**으로 가면 차별화된다.

## 1.4 단계별 진행 순서

처음부터 서버 동기화까지 넣으면 무겁다.

### 0단계. 로컬 앱 먼저

처음부터 서버 만들지 말고, 먼저 로컬에서 완전히 쓸 수 있어야 한다. 필수 기능은 이 정도다.

- 카드 생성
- 덱 생성
- 태그 추가
- 오늘 복습 카드 조회
- 복습 결과 저장
- Again / Hard / Good / Easy 버튼
- 다음 복습일 계산
- 오답 카드 모아보기
- 카드 검색

이것만 돼도 이미 SRS 앱이다. 여기서 중요한 건 **동작하는 작은 앱을 빨리 만드는 것**이다.

### 1단계. AX 차별화 기능 추가

그다음부터 Neo-Anki스러운 기능을 넣으면 된다. 가장 추천하는 건 **카드 수리함**이다.

자동 분류 기준 예시.

- 3번 이상 Again을 누른 카드
- 평균 응답 시간이 긴 카드
- 최근 7일 안에 반복적으로 틀린 카드
- 앞면이 너무 긴 카드
- 뒷면이 너무 긴 카드

별도 화면에서 이렇게 보여준다.

```text
수리 필요 카드 12개

1. 답변이 너무 긴 카드
2. 자주 틀리는 카드
3. 질문이 애매한 카드
4. 너무 오래 방치된 카드
```

LLM 없이도 충분히 가능하다. 이게 진짜 AX다. 사용자가 복습만 하는 게 아니라 **자기 카드 품질을 관리하게 만드는 것**.

### 2단계. 동기화 서버 추가

이때 서버 역할은 딱 이것만이다.

- 계정 관리
- 덱 동기화
- 카드 동기화
- 복습 로그 동기화
- 미디어 파일 동기화
- 백업

**절대 서버에서 카드 생성, 추천, AI 처리 같은 건 하지 않는다.**

```text
Client
- SQLite / IndexedDB
- 카드 DB
- 복습 로그
- 스케줄러
- 오프라인 복습
- 로컬 검색

Server
- User
- Deck
- Card
- ReviewLog
- Media
- Sync State
```

처음에는 충돌 해결도 단순하게 간다.

| 대상 | 정책 |
|---|---|
| 카드 내용 충돌 | `updated_at`이 더 최신인 쪽 우선 |
| 복습 로그 | append-only로 모두 저장 |
| 삭제 | `deleted_at`으로 soft delete |
| 미디어 | hash 기준 중복 제거 |

복잡한 CRDT까지 처음부터 갈 필요 없다.

## 1.5 MVP 기능

> **목표.** LLM API 없이, 로컬에서 작동하는 가벼운 SRS 복습 앱을 만든다.

**1차**

- 덱 만들기
- 카드 만들기
- 태그 달기
- 오늘 복습 카드 보기
- Again, Hard, Good, Easy로 복습하기
- 복습 결과에 따라 다음 복습일 계산하기
- 자주 틀린 카드 모아보기
- 카드 검색
- 간단한 학습 통계
- 로컬 저장

**2차**

- 로그인
- 여러 기기 동기화
- 카드 백업
- 복습 로그 동기화
- 미디어 파일 동기화

## 1.6 차별화 기능 3개

너무 많은 기능 넣지 말고, 처음에는 이 3개를 중심으로 잡는 게 좋다.

### 1. 복습 부담 줄이기

Anki는 "오늘 카드 187개" 이런 식으로 사용자에게 압박을 준다. Neo-Anki는 이걸 다르게 보여줄 수 있다.

```text
오늘 최소 복습: 12장
권장 복습: 38장
전체 밀린 카드: 121장
```

그리고 모드 선택.

- 5분만 하기
- 최소치만 하기
- 어제 틀린 것만 하기
- 시험 전 몰아보기
- 새 카드 없이 복습만 하기

이건 진짜 사용자 체감이 크다.

### 2. 카드 수리함

앞에서 말한 것처럼 나쁜 카드를 따로 모아주는 기능. 이게 있으면 단순 암기 앱이 아니라 학습 관리 앱처럼 보인다.

```text
이 카드는 최근 5번 중 4번 틀렸어요.
질문이 너무 넓거나 답변이 너무 길 수 있어요.
```

LLM 없이도 이런 문구는 rule-based로 충분히 가능하다.

### 3. Inbox 기반 카드 생성

카드를 바로 완성하려고 하면 피곤하다. 대신 **일단 던져놓는 공간**을 만들면 좋다.

```text
Inbox
- 오늘 강의에서 추가한 개념
- 논문 읽다가 저장한 문장
- 시험 범위에서 뽑은 용어
- 나중에 카드로 바꿀 내용
```

그다음 사용자가 직접 카드로 변환한다. 이건 실제로 자료 정리하고 Anki 카드 만들 때 겪는 불편이랑도 잘 맞을 것이다.

## 1.7 기술 스택 추천

사이드프로젝트 기준으로는 너무 엔터프라이즈하게 가지 않는 게 좋다.

| | 선택지 A. 웹앱 중심 | 선택지 B. 데스크톱 중심 | 선택지 C. 모바일 중심 |
|---|---|---|---|
| Client | React / Next.js | Tauri + React | Flutter |
| Local DB | IndexedDB | SQLite | SQLite / Isar |
| Server | Spring Boot 또는 FastAPI | Spring Boot / FastAPI | Spring Boot / FastAPI |
| DB | PostgreSQL | PostgreSQL | PostgreSQL |
| 장점 | 만들기 쉽고 보여주기 좋음 | Anki 대체 느낌이 강함 | 실제 복습 경험에 제일 가까움 |
| 단점 | 모바일 앱 같은 느낌은 약함 | 모바일은 따로 만들어야 함 | 개발 러닝커브 |

선택지 A에는 Auth로 JWT / Session, 배포는 Render, Railway, Fly.io, Supabase 등을 붙인다.

**추천은 웹앱 먼저.** 처음부터 모바일 앱, 데스크톱 앱, 동기화까지 다 하면 너무 커진다. 일단 웹에서 local-first처럼 동작하는 MVP를 만들고, 나중에 Tauri나 모바일로 확장하는 게 현실적이다.

> ⚠️ 이 판단은 **Part 2에서 정반대로 뒤집힌다.** Anki 호환성을 넣기로 하면서 Note/Card 분리가 필수가 된다.

## 1.9 스케줄러 정책

처음부터 FSRS까지 완벽히 구현하려고 하지 않아도 된다. MVP에서는 이런 식으로 충분하다.

| 평가 | 다음 간격 |
|---|---|
| Again | 10분 뒤 또는 오늘 다시 |
| Hard | `interval * 1.2` |
| Good | `interval * ease` |
| Easy | `interval * ease * 1.5` |

카드마다 관리할 값.

- `interval`
- `ease`
- `due_at`
- `review_count`
- `lapse_count`

중요한 건 알고리즘 정확도보다 **복습 흐름이 자연스러운가**다.

> ⚠️ 이 제안은 이후 확정된 `SRS-preserving`(검증된 SRS 재사용, 직접 만들지 않음) 원칙과 충돌한다. ADR 0001에서 다시 판단할 것.

## 1.10 기획 문장

> Neo-Anki는 LLM API 없이 작동하는 local-first SRS 학습 앱입니다. 기존 암기 앱이 복습 알고리즘 자체에 집중했다면, Neo-Anki는 사용자가 매일 복습을 시작하고, 나쁜 카드를 고치고, 학습 자료를 정리하는 전체 경험을 개선하는 데 초점을 둡니다. 서버는 AI 처리나 카드 생성이 아닌, AnkiWeb처럼 카드와 복습 기록을 여러 기기에서 동기화하기 위한 목적으로만 사용됩니다.

더 짧게.

> LLM 없이도 매일 쓰기 편한 local-first SRS 학습 앱.

또는.

> 복습 부담과 카드 관리 피로를 줄이는 개인용 Anki 대체 앱.

## 1.11 Part 1 결론

1안을 사이드프로젝트로 가져가는 건 괜찮다. 오히려 가장 현실적이다. 다만 목표를 이렇게 잡아야 한다.

| | |
|---|---|
| 하지 말아야 할 것 | Anki보다 **기능 많은** 앱 만들기 |
| 해야 할 것 | Anki보다 **덜 피곤한** 앱 만들기 |

MVP 기준으로는 로컬 카드 생성, 복습, 오답 로그, 카드 수리함까지만 만들어도 충분히 프로젝트로 의미 있다. 그다음 서버 동기화를 붙이면 "진짜 서비스 구조"가 되고, 포트폴리오로도 꽤 탄탄해진다.

# Part 2. Anki 호환성 도입

> **작성자**
>
> 그런데 anki와의 덱 호환성을 가져가고 싶어

덱 호환성을 가져가려면 제품 난이도가 꽤 올라가지만, 방향은 좋다. 여기서 중요한 건 "Anki를 완전 재현"이 아니라 **import/export 범위를 명확히 제한하는 것**이다.

## 2.1 방향 전환

1안도 완전히 버리지 않고, "독립 앱이지만 Anki와 왕복 가능한 앱"으로 잡으면 된다. 오히려 이게 가장 좋아 보인다.

> Neo-Anki는 자체 SRS 앱이다.
> 다만 사용자가 기존 Anki 덱을 가져올 수 있고, 필요하면 다시 Anki로 내보낼 수 있다.
> 즉, Anki 클론이 아니라 **Anki-compatible local-first SRS 앱**이다.

이러면 독립 앱의 자유도와 Anki 생태계의 신뢰를 둘 다 가져갈 수 있다.

## 2.2 핵심 결론

Anki 호환성은 가져가는 게 좋다. 다만 처음부터 완전 호환을 목표로 하면 프로젝트가 터질 가능성이 높다.

Anki의 `.apkg`는 단순 카드 묶음이 아니라 cards, notes, note types, media, scheduling information까지 포함할 수 있는 패키지다. Anki 공식 문서에서도 `.apkg`를 단일 덱과 하위 덱을 내보내는 Anki Deck Package로 설명하고, 패키지 안에는 카드, 노트, 노트 타입, 이미지나 사운드 같은 미디어가 포함될 수 있다고 설명한다.

그래서 목표를 이렇게 나눠야 한다.

| 순서 | 목표 |
|---|---|
| 1차 | Anki 덱을 가져와서 Neo-Anki에서 학습 가능하게 만들기 |
| 2차 | Neo-Anki 덱을 Anki에서 열 수 있는 `.apkg`로 내보내기 |
| 3차 | 스케줄링 기록까지 최대한 보존하기 |

3차는 나중에. MVP에서는 1, 2까지만 해도 충분히 강하다.

## 2.3 제일 중요한 설계 변경. Card 중심으로 만들면 안 된다

Anki와 호환하려면 데이터 모델을 Anki식으로 어느 정도 따라가야 한다.

Anki는 단순히 front/back 카드만 있는 구조가 아니다. **기본 단위는 Note이고, Note가 하나 이상의 Card를 만들어낸다.** genanki 문서에서도 Anki의 기본 단위는 Note이며, 하나의 Note가 하나 이상의 Card에 대응한다고 설명한다.

```text
Note
- Front: "capital of Korea"
- Back: "Seoul"

Template
- 앞면: {{Front}}
- 뒷면: {{FrontSide}} <hr> {{Back}}

Card
- 실제 복습되는 카드
```

더 복잡한 경우에는 하나의 노트에서 여러 카드가 나온다.

```text
Note
- Korean: 사과
- English: apple
- Example: I ate an apple.

Card 1: Korean → English
Card 2: English → Korean
Card 3: Example cloze
```

그래서 Neo-Anki를 처음부터 이렇게 설계하는 게 좋다.

```text
Deck
NoteType
NoteField
CardTemplate
Note
Card
ReviewLog
MediaAsset
Tag
```

처음에는 귀찮아 보여도, 이렇게 안 하면 나중에 Anki 호환성 붙일 때 구조를 갈아엎게 된다.

## 2.5 호환성은 단계적으로

### Level 1. `.apkg` import, 내용만 가져오기

가장 먼저 해야 할 건 이것이다.

```text
.apkg 업로드
→ 압축 해제
→ collection.anki2 / collection.anki21 / collection.anki21b 확인
→ SQLite에서 deck, note type, note, card 읽기
→ media 매핑 읽기
→ Neo-Anki 내부 모델로 변환
```

`.apkg`는 기술적으로 ZIP 아카이브 형태이고, 내부에 SQLite DB와 미디어 매핑 파일이 들어가는 구조로 다뤄진다. 예컨대 기존 APKG 파서 문서들은 `collection.anki2`, 미디어 파일들, media JSON 매핑 파일을 핵심 구성요소로 설명한다.

이 단계에서는 스케줄링 기록은 무시해도 된다. 우선은 "카드 내용, 덱 구조, 태그, 이미지, 오디오가 잘 들어온다"가 목표다.

### Level 2. Neo-Anki → `.apkg` export

이건 꽤 포트폴리오적으로 좋다.

사용자가 Neo-Anki에서 만든 덱을 `.apkg`로 내보내서 Anki에서 열 수 있게 만드는 것이다. Python 쪽에서는 genanki 같은 라이브러리가 Anki 덱 생성을 지원하고, `Package(...).write_to_file('output.apkg')` 형태로 Anki에서 import 가능한 패키지를 만들 수 있다.

MVP에서는 직접 Anki 패키지 포맷을 다 구현하지 말고, export는 라이브러리 도움을 받는 게 현실적이다.

### Level 3. Scheduling 정보 일부 호환

이건 나중에.

Anki 공식 문서에 따르면 `.apkg` export 시 scheduling information을 포함할 수 있고, 포함하지 않으면 review history, marked, leech tags 같은 스케줄 관련 정보가 제거된다.

즉, Anki 덱에는 단순 카드 내용뿐 아니라 복습 이력도 들어갈 수 있다. 하지만 이걸 완전히 호환하려면 `revlog`, `cards.due`, `ivl`, `ease`, `queue`, `type` 같은 개념을 Neo-Anki 스케줄러와 맞춰야 해서 난이도가 확 올라간다.

그래서 MVP에서는 이렇게 선언하는 게 좋다.

> 현재 버전은 Anki 덱의 카드 내용, 덱 구조, 태그, 미디어를 가져옵니다.
> 복습 이력과 스케줄링 상태는 Neo-Anki 스케줄러 기준으로 새로 시작됩니다.

이건 충분히 납득 가능한 정책이다.

## 2.6 MVP 호환 범위

처음부터 모든 Anki 기능을 지원하지 말고, 명확히 제한해야 한다.

| 항목 | MVP 지원 여부 | 이유 |
|---|---|---|
| Basic 카드 | 지원 | 가장 기본 |
| Basic reversed | 지원 | 구조 단순 |
| Cloze | 가능하면 지원 | 사용자가 많음 |
| 태그 | 지원 | 중요하고 쉬움 |
| 덱 계층 | 지원 | 부모::자식 구조 보존 |
| 이미지 | 지원 | 체감 큼 |
| 오디오 | 2순위 지원 | 언어 학습에서 중요 |
| 커스텀 CSS | 보존은 하되 완전 렌더링은 2순위 | 예상치 못한 깨짐 많음 |
| 커스텀 JS | 비지원 또는 제한 | 보안, 렌더링 이슈 |
| Image Occlusion | 비지원 | 애드온 의존 가능성 큼 |
| 복습 이력 | MVP 비지원 | 난이도 높음 |
| FSRS / Anki 스케줄 상태 | MVP 비지원 | 독립 앱의 스케줄러와 충돌 |
| Add-on 특수 필드 | 비지원 | 범위 초과 |

핵심은 "안 되는 걸 숨기는 것"이 아니라, **지원 범위를 명확히 고지하는 것**이다.

## 2.7 정체성 변화

| | |
|---|---|
| 기존 | LLM 없이 작동하는 독립 SRS 앱 |
| 변경 | **Anki 덱을 가져와 더 편하게 복습하고 관리할 수 있는 local-first SRS 앱** |

이게 훨씬 강하다. 사용자가 새 앱을 쓸 때 제일 큰 장벽은 "내가 기존에 쌓아둔 자료를 버려야 하나?"이기 때문이다. Anki 호환성을 제공하면 이 장벽이 크게 낮아진다.

### 제품 전략

Anki 호환성을 "Anki 대체"로 말하면 부담이 커진다. 대신 이렇게 말하는 게 좋다.

> Anki를 쓰던 사람도 부담 없이 가져와서 써볼 수 있다.
> 마음에 안 들면 다시 Anki로 내보낼 수 있다.

이게 사용자에게 안정감을 준다. 포지셔닝은 이렇다.

```text
Not Anki clone
Not AI flashcard generator
Not AnkiWeb replacement

→ Anki-compatible, local-first review workspace
```

## 2.8 구현 순서

| 단계 | 내용 |
|---|---|
| 1단계 | Neo-Anki 자체 모델 먼저 만들기. 단, 처음부터 Anki 호환 가능한 구조로 |
| 2단계 | Basic 카드 직접 생성 기능 |
| 3단계 | `.apkg` import |
| 4단계 | `.apkg` export |
| 5단계 | round-trip 개선 |

**1단계.** `Deck`, `NoteType`, `Note`, `Card`, `ReviewLog`, `Media`. 이 구조 없이 `Card(front, back)`로 시작하면 나중에 힘들어진다.

**2단계.** 먼저 Neo-Anki 내부에서 다음이 되어야 한다. 덱 생성, 노트 생성, 카드 렌더링, 복습, 리뷰 로그 저장, 검색, 태그.

**3단계.** 처음 지원 범위는 Basic, Basic reversed, Cloze, Deck hierarchy, Tags, Image media.

**4단계.** 처음에는 Neo-Anki에서 만든 카드만 안정적으로 export. Anki에서 가져온 복잡한 커스텀 덱을 다시 lossless export하는 건 나중으로 미뤄야 한다.

**5단계.** Anki import → Neo-Anki 수정 → Anki export, 원본 note type 보존, 원본 template 보존, media filename 보존, `anki_guid` 보존. 이때부터 "왕복 호환"이라고 말할 수 있다.

## 2.9 제일 피해야 할 함정

가장 위험한 방향은 이것이다.

> `.apkg` 완전 호환부터 만들기

그러면 앱이 아니라 **파일 포맷 파서 프로젝트**가 되어버린다.

핵심은 AX다. 그러면 Anki 호환성은 진입 장벽을 낮추는 bridge여야지, 프로젝트의 본체가 되면 안 된다.

## 2.10 Part 2 결론

MVP 문장은 이렇게 가면 된다.

> Neo-Anki는 Anki `.apkg` 덱을 가져와 로컬에서 복습할 수 있는 독립 SRS 앱입니다. 초기 버전은 카드 내용, 덱 구조, 태그, 미디어를 중심으로 호환하며, 복습 스케줄과 리뷰 이력은 Neo-Anki의 자체 스케줄러로 새롭게 관리합니다.

방향 정리.

- 독립 앱 + Anki import/export 지원
- 완전한 Anki 재구현 ✗
- Anki 생태계와 연결되는 Neo-Anki식 복습 경험 ✓

MVP의 핵심 차별점은 여전히 이 5개다.

1. Anki 덱 가져오기
2. 더 편한 복습 화면
3. 복습 부담 줄이기
4. 자주 틀리는 카드 수리함
5. 다시 Anki로 내보내기

이렇게 잡으면 사이드프로젝트로도 충분히 크고, 포트폴리오로도 "단순 CRUD"가 아니라 파일 포맷 호환, 로컬 DB, SRS 알고리즘, 동기화, UX 개선이 들어간 꽤 탄탄한 프로젝트가 된다.

# Part 3. 기획 초안

> **작성자**
>
> 기획을 해볼까?

방향은 이렇게 정리한다.

> Neo-Anki는 Anki 덱을 가져와 더 편하게 복습하고 관리할 수 있는 local-first SRS 학습 앱이다.
> LLM API 없이 동작하며, 서버는 AnkiWeb처럼 카드, 미디어, 복습 로그 동기화를 위한 용도로만 사용한다.

## 3.1 문제 정의

Anki는 강력한 SRS 학습 도구지만, 실제 사용자 경험에는 몇 가지 불편이 있다.

**첫째, 진입 장벽이 높다.**
덱, 노트 타입, 카드 템플릿, 태그, 필드 구조가 강력한 대신 초보자에게는 복잡하게 느껴진다.

**둘째, 복습 부담이 크다.**
사용자는 앱을 켰을 때 "오늘 복습할 카드 수"를 보고 압박감을 느낀다. 결국 복습을 시작하지 못하거나, 밀린 카드가 누적되면서 앱을 이탈한다.

**셋째, 나쁜 카드가 계속 누적된다.**
질문이 애매하거나 답변이 너무 긴 카드도 계속 복습 큐에 남는다. 사용자는 카드를 고쳐야 한다는 사실은 알지만, 어떤 카드를 어떻게 고쳐야 하는지 관리하기 어렵다.

**넷째, 기존 자료 이전이 어렵다.**
Anki 사용자는 이미 많은 덱을 가지고 있기 때문에, 새로운 SRS 앱으로 이동하기 어렵다. 따라서 Anki 덱 호환성은 필수적인 신뢰 요소가 된다.

## 3.2 제품 컨셉

**한 줄 소개**

> Anki 덱을 가져와 더 편하게 복습하고 관리하는 local-first SRS 앱

**조금 더 긴 설명**

Neo-Anki는 LLM API 없이 작동하는 독립형 SRS 학습 앱이다. 기존 Anki의 반복학습 철학은 유지하되, 복습 진입, 카드 정리, 오답 관리, 카드 수정 경험을 더 단순하게 만든다. 사용자는 Anki `.apkg` 덱을 가져와 Neo-Anki에서 복습할 수 있으며, 서버는 AI 처리나 카드 생성이 아닌 여러 기기 간 동기화와 백업을 담당한다.

## 3.3 핵심 사용자

### 1차 타겟. Anki를 써봤지만 부담을 느낀 사용자

이 사용자는 이미 SRS의 가치를 알고 있다. 하지만 Anki의 UI, 덱 관리, 복습량 압박 때문에 꾸준히 사용하지 못했을 가능성이 높다.

- 시험 공부를 위해 Anki를 써본 대학생
- 어학 단어장을 Anki로 관리해본 사용자
- 의학, 법학, 자격증 공부처럼 암기량이 많은 사용자
- Anki 덱은 있지만 복습 루틴이 자주 무너지는 사용자

### 2차 타겟. Anki는 모르지만 반복학습 앱이 필요한 사용자

이 사용자는 처음부터 복잡한 노트 타입이나 템플릿을 원하지 않는다. 그냥 쉽게 카드를 만들고, 매일 조금씩 복습하고 싶어 한다.

## 3.4 핵심 가치 제안

Neo-Anki의 가치는 "AI 카드 생성"이 아니다. 핵심은 **복습 지속성**이다.

| 가치 | 설명 |
|---|---|
| Anki 호환성 | 기존 Anki 덱을 가져올 수 있어 진입 장벽이 낮다 |
| Local-first | 오프라인에서도 복습 가능하고, 개인 학습 자료가 로컬에 남는다 |
| 낮은 복습 부담 | 전체 카드 수보다 오늘 할 수 있는 최소 단위에 집중한다 |
| 카드 수리 경험 | 자주 틀리는 카드, 답변이 긴 카드, 애매한 카드를 따로 관리한다 |
| LLM API 없음 | 비용, 개인정보, 네트워크 의존성을 줄인다 |
| 동기화 전용 서버 | 서버는 카드와 복습 로그 동기화만 담당한다 |

## 3.5 MVP 범위

처음부터 완전한 Anki 대체제를 만들면 범위가 너무 커진다.

> **MVP 목표.** 사용자가 Anki 덱을 가져오거나 직접 카드를 만들어, 로컬에서 복습하고, 자주 틀리는 카드를 관리할 수 있게 한다.

### 3.5.1 덱 관리

- 덱 생성
- 덱 수정
- 덱 삭제
- 덱별 카드 수 표시
- 오늘 복습할 카드 수 표시

### 3.5.2 카드 생성

- Basic 카드 생성
- Front / Back 입력
- 태그 입력
- 덱 선택
- 카드 수정
- 카드 삭제

### 3.5.3 복습

- 오늘 복습 카드 조회
- Again / Hard / Good / Easy 버튼
- 응답 시간 기록
- 다음 복습일 계산
- 복습 완료 화면

### 3.5.4 카드 수리함

자주 틀리거나 품질이 낮아 보이는 카드를 별도 화면에 모은다. 초기 기준은 rule-based로 충분하다.

- 최근 5회 중 3회 이상 Again
- 평균 응답 시간이 긴 카드
- Front가 지나치게 긴 카드
- Back이 지나치게 긴 카드
- 30일 이상 복습되지 않은 카드

### 3.5.5 Anki 덱 가져오기

초기 지원 범위.

- `.apkg` import
- Basic 카드
- Basic reversed 카드
- Cloze 카드 일부 지원
- 덱 계층 구조
- 태그
- 이미지 미디어

초기에는 복습 이력과 Anki 스케줄링 상태를 가져오지 않아도 된다. 명확히 이렇게 정책을 잡으면 된다.

> Neo-Anki v0.1은 Anki 덱의 카드 내용, 덱 구조, 태그, 미디어를 가져옵니다. 복습 이력과 스케줄링 상태는 Neo-Anki의 자체 스케줄러 기준으로 새롭게 시작됩니다.

### 3.5.6 로컬 저장

처음에는 서버 없이도 작동해야 한다. 카드 DB, 덱 DB, 복습 로그, 설정, 미디어 파일.

## 3.6 MVP에서 제외할 것

초기 버전에서 제외해야 하는 기능도 명확히 잡아야 한다.

| 기능 | 제외 이유 |

| 소셜 기능 | 학습 지속성과 직접 관련이 약함 |

## 3.10 스케줄러 정책

## 3.13 프로젝트 차별점

Neo-Anki의 차별점은 기능 수가 아니다. 핵심 차별점은 다음 3개다.

**1. Anki 호환성.** 사용자는 기존 Anki 덱을 버리지 않아도 된다.

**2. 복습 부담 완화.** 전체 할 일을 보여주는 대신, 사용자가 지금 할 수 있는 작은 단위로 복습을 시작하게 한다.

**3. 카드 수리함.** 단순히 틀린 카드를 다시 보여주는 것이 아니라, 자주 틀리는 카드를 고쳐야 할 대상으로 보여준다.

## 4라운드. 어려운 카드

### Q1. 계속 틀리는 카드가 나왔을 때 보통 어떻게 해?

*그냥 Again 누르고 반복해, 잠깐 멈춰서 이해하려고 해, 자료로 돌아가, 카드 내용을 수정해, 아니면 일단 넘겨?*

**답변**

보통 "암기"를 못한 카드인 경우가 계속 틀리는 카드인 경우가 대다수임. again 누르고 반복하다가 계속 기억을 못하면 그냥 skip하고 아예 나중에 다시 학습하는 것 같아. 개인의 차이가 있기는 하겠지만, 나의 경우에는 보통 뭔가를 이해하지 못한 경우에는 애초에 anki로 공부하지 않는 것 같아. 일단 개념에 대한 명확한 그림이 그려진 이후에 anki로 외우는 편이고. 이해가 필요하지 않은 단순 암기 위주의 과목과 시험 준비는 굳이 자료로 돌아가더라도 더 얻을 수 있는 팁이 없다고 느껴. 카드의 내용이 길고 복잡한 경우에는 차라리 단순화시키는 방향으로 카드를 수정해서 최대한 부하를 적게 주려고 하는 것 같아.

### Q2. 어려운 카드가 어려운 이유는 보통 뭐야?

**답변**

다양한 케이스가 물론 있지만, 가장 대표적인 사례를 꼽아볼게. 먼저 "헷갈림" 케이스가 있어. 이 경우에는 그냥 질문과 답이 서로 매칭이 안되는 경우야. 예를 들어서 A의 속성 4가지와 각 속성의 예시가 있다고 했을 때, 각 속성과 예시가 엇갈리게 매칭되거나 해서 헷갈려하는 것 때문에 고생하는 경우가 있음. 그러나 이건 지속적인 반복이 가장 중요하고, 자료나 해설 등을 통해 확실히 공부하는 것이 효과적이더라. 두번째는 "머리에 안들어와" 케이스가 있음. 그냥 순수하게 아무리 봐도 머릿속에 들어오지 않는 거야. 정말 단순한 단어이거나 문장일 때도 물론 있지만, 그것보다는 계속 말했듯이 내용 자체가 하나의 카드에 너무 많을 때가 가장 어려운 것 같아. 물론 이걸 카드 여러개로 쪼갤 수도 있겠지만, "A의 속성을 설명하라" 이런식의 앞면이 나오면 각 속성을 전부 알아야 함은 물론 각 속성에 대한 설명도 알아야하기 때문에 하나로 LLM이 만들어주더라. 이걸 카드로 일일이 내가 다시 분해하기엔 또 귀찮더라.

### Q3. "이 카드는 지금 붙잡고 있으면 손해다"라고 느끼는 순간이 있어? 있다면 그때 Anki가 어떻게 해줬으면 좋겠어?

**답변**

카드에서 우선순위를 정해주면 너무 좋을 것 같아. 지금은 anki에서 하나의 카드 덱 전체를 사이클로 돌리는데, 우선순위를 더 많이 보여준다거나 덱 내에서 우선순위 필터링을 해서 그거 위주로만 먼저 회독을 할 수 있도록 한다거나 하는 방향도 좋을 것 같아. 1순위를 해치우면, 디테일과 고득점 혹은 높은 이해를 위해 2순위로 넘어간다던지 하는 식의 방법도 생각해볼 수 있겠어. 더 창의적이고 효과적인 방법을 함께 강구해보자. 쉬운걸 먼저 한다던지, 쪼개기 제안, 키워드 위주 학습 등 너의 예시도 좋은 방법이 될 듯.

### Q4. 반대로 "이 카드는 반드시 잡고 가야 한다"고 느끼는 카드도 있어?

**답변**

물론. 무조건 출제될 것 같은 포인트들(교수 강조, 기출 이력 有, 핵심 개념 등)이 있어서 이것들에 조금 더 집중하고 싶을 때도 많아. 보통 LLM에게 전달하는 파일에 수기로 별표가 쳐져 있거나 하이라이트, 붉은 글씨 등으로 강조를 해 놓는 경우가 많아.

### Q5. 틀린 카드가 쌓였을 때, 너는 '반복'이 더 필요하다고 느껴? 아니면 '카드 재구성'이 더 필요하다고 느껴?

**답변**

제대로된 카드 구성일 경우에는 반복이 더 우선될 필요가 있다고 생각해. 그러나, 카드 자체가 너무 길거나 복잡하고 명료하지 않을 때에는 저품질의 카드를 억지로 외우기보다는 재구성하는게 더 낫다고 생각해. 답변을 더 쪼개서 카드 하나하나의 부담을 줄이고, 힌트를 주는 방식도 나쁘지는 않다고 봄. 아니면 힌트 자체보다는 너무 어려워하면 관련 해설을 원자료 기반으로 제시해서 다시 한번 짚어주는 세션이 있어도 좋을 것 같아. 그림과 같은 멀티미디어도 정말 좋은 방법이지. 유튜브 영상이나 웹에서 있는 다양한 그림 혹은 글들을 레퍼런스로 들고 와도 좋을 것 같아

## 5라운드. 덱 운영과 학습 재개

### Q1. 시험이나 자격증이 끝난 뒤 덱은 어떻게 처리해?

*그대로 보관해, 삭제해, 숨겨둬, 가끔 다시 봐, 아니면 다음 시험 때 일부를 재활용해?*

**답변**

기말고사 범위가 중간고사 범위를 포함하는 경우에는 보관해놨다가 다시 보지만, 일반적으로 시험이 끝나거나 자격증을 취득한 이후에는 다시 보지 않음. anki web에는 보관은 하고 있긴한데, 보지 않음. 예전에는 끝나면 삭제해버렸었는데 지금은 일단 지난 학기 내용 유지 중. 뭔가 다른 사람이랑 덱을 공유할 수 있거나 공동 프로젝트 형식으로 할 수 있어도 재미있을 듯.

### Q2. 며칠 동안 Anki를 못 해서 복습 카드가 많이 밀리면 어떻게 해?

*밀린 카드를 전부 처리하는지, 일부만 보는지, 스케줄을 초기화하는지, 아예 덱을 포기한 적도 있는지 궁금해.*

**답변**

보통은 내 성격 상 전부 처리하려고 할 거지만, 시간적 여유가 부족하면 일부만 보고 차차 그 밀린 내역들을 해치워나가지 않을까 생각함. 초기화나 포기는 생각하지 않아.

### Q3. 덱과 카드를 어떤 기준으로 정리해?

*과목, 시험, 챕터, 자료 출처, 중요도, 카드 유형 등으로 나누는 편이야? 태그나 하위 덱도 실제로 활용해?*

**답변**

[첨부한 스크린샷을 참조] 기본적으로 과목 혹은 자격증 별로 구분하고 그 안에서 세부적으로 챕터 단위 혹은 공부하는 단위(모의고사 시험지, 강의 순서)에 따라 구분하는 것 같아. 태그는 솔직히 활용하는 방법을 몰라서 활용 못하고 하위 덱은 사용중. 근데 이것도 그냥 디렉토리처럼 활용하는거라서 그 이상의 활용은 잘 몰라.

### Q4. 기기 간 사용이나 파일 관리에서 불편한 점이 있었어?

*PC와 모바일 동기화, 미디어 파일, CSV import, 덱 내보내기, 백업, Anki 버전 차이 같은 부분.*

**답변**

anki web이 있어서 종료할 떄 자동으로 진행상황을 동기화해주니까 그 부분이 되게 좋았음. ios의 경우에는 앱이 유료라서 모바일 웹을 활용했음. 카드에서 사진을 넣었을 때 글자 대비 사진이 너무 큰 경우가 많아서 시인성이 좋지 않았음. 외부에서 파일 작업해서 카드를 통째로 업로드 할 때도 뭔가 csv나 이런식으로 올리는데 이럴거면 json이 낫지 않나라는 생각이 있었어. 덱 내보내기는 잘 안써봤음. 말했듯이 anki web이 있으니까. 백업도 굳이라는 생각? 그런데 anki web 말고 개인 드라이브나 깃허브 처럼 다른 클라우드 옵션이 있어도 좋을 것 같아.

### Q5. 오늘 무엇을 공부할지 정할 때 어떤 정보가 보이면 좋겠어?

*예를 들어 시험까지 남은 날짜, 핵심 카드 학습률, 아직 보지 않은 범위, 계속 틀리는 카드, 예상 학습량 같은 것들.*

**답변**

제시한 내용들 전부 마음에 들어. 깃허브에서 있는 공부량 체크하는 그런 매트릭스? 히트맵도 플러그인 형태로 anki에서 있는데 이런것도 기본 지원하고, 뭔가 이런 다양한 지표를 시각화해서 명확한 목표와 현상태에 대한 피드백이 있으면 너무 좋을 것 같아.

> **진행자 메모.** 스크린샷을 보니 실제로 과목 → 시험 또는 학습 단위 → 챕터 구조로 하위 덱을 디렉터리처럼 쓰는 방식도 확인됐다. 태그나 필터 기능보다는 눈에 보이는 계층 구조에 의존하는 편이다.

## 6라운드. 학습 통제와 확장 방식

> 원문에는 질문 목록이 두 번 반복되어 있었다. 답변이 있는 쪽으로 병합했다.

### Q1. Anki를 실행했을 때 앱이 오늘 공부할 내용을 알아서 정해주는 편이 좋아, 아니면 네가 범위와 순서를 직접 선택하는 편이 좋아?

*자동 추천을 받더라도 반드시 직접 조정할 수 있어야 하는지도 궁금해.*

**답변**

사전에 스케줄링을 할 수 있고 그 스케줄에 따라서 진행하면 좋을 것 같음. 앱이 직접 스케줄을 추천해주는 방법도 있으면 좋을 것 같아. 그럼에도 불구하고 사용자가 직접 범위와 순서를 언제든지 조정할 수 있고 변화된 일정과 학습 내역에 따라 능동적으로 스케줄이 변화했으면 좋겠어.

### Q2. Again, Hard, Good, Easy 네 단계는 실제로 명확하게 구분해서 사용해?

*어떤 기준으로 선택하는지, 혹은 판단 단계가 너무 많거나 애매하다고 느낀 적은 없는지.*

**답변**

명확하다고 생각함. 아예 모르겠으면 again, 몇개가 기억이 안나거나 디테일 부족할 때 hard, 기억해냈으면 good, 보자마자 모든게 떠오르고 쉽다면 easy로 분류. 0-9점 식으로 해도 뭐 가능은 하겠지만 오히려 이게 나한테는 스트레스로 다가올 수 있다고 생각해. 난 선택을 어려워하는데 이걸 수치적으로 보여준다면 그 기준이 명확하지 않으니까... 지금 단계로도 만족하긴 하지만, 더 좋은 방법론이 있다면 언제든 열려있음.

### Q3. 한 번의 학습 세션이 언제 끝나야 한다고 생각해?

*오늘 예정된 카드를 모두 끝냈을 때, 설정한 시간이 지났을 때, 핵심 범위를 한 번 돌았을 때, 집중력이 떨어졌을 때 등.*

**답변**

학습 세션은 그날 전체의 학습을 의미하는게 아니겠지? 한 번 덱에 들어갔다가 나올 때까지를 하나의 세션이라고 봤을 때는 가장 베스트는 사실 "예정된 모든 카드를 끝냈을 때"이지. 그러나, 시간적인 한계도 있고 사람의 집중력이 항상 최고점에 있을 수 없기 때문에, 핵심 범위를 다 돌았거나 집중력이 떨어졌을 때를 파악할 수만 있다면 그 때 일단 멈추고 리프레시 하는 시간을 가질 수 있도록 도와주는 것도 좋을 것 같아. 학습하는 양도 물론 중요한데, 뇌의 피로를 최소화하면서 최적화된 스케줄과 구성으로 극강의 효율을 뽑아내는 것이 무엇보다 중요한 요소라고 생각해

### Q4. 학습 통계 중 실제로 행동을 바꿀 만한 정보는 무엇일까?

*단순 공부 시간이나 연속 학습일보다, 시험 준비도·핵심 범위 숙달률·취약 개념·예상 완료일 같은 정보가 더 중요한지도 궁금해.*

**답변**

"시험 준비도·핵심 범위 숙달률·취약 개념·예상 완료일 같은 정보"가 더 나에겐 도움이 되는 정보일거라고 생각해. anki의 사용자는 꾸준한 학습 그 자체보다는 어떤 실질적 목표(성적, 자격증 등)가 있어서 그 목표를 성취하기 위한 수단이라고 생각해. 물론 사용자가 어떻게 쓰냐에 따라 다르겠지만! 만약 공유 덱 같은게 가능해서 같이 공부하는 사람이 있다면 다른 사람은 얼마나 열심히 하고 있는지, 나는 그들 중에서 어느정도에 위치하는지에 대한 그런 비교가 가능해도 뭔가 경쟁의식을 통한 모티베이션이 가능하지 않을까? 이것도 더 다양한 레퍼런스를 찾아봐야겠어.

### Q5. 덱 공유나 공동 프로젝트를 한다면 어떤 형태를 상상해?

*한 덱을 함께 편집하기, 다른 사람의 카드를 가져와 내 방식으로 수정하기, 좋은 카드에 평가·댓글 남기기, 수정 사항을 버전처럼 관리하기 중 어떤 것이 가장 유용할 것 같아?*

**답변**

하나의 덱을 함께 편집하는 것이 아마 가장 기본적인 형태가 되겠지? 그러나, 참여자가 늘어날 수록 이 방법은 덱의 퀄리티를 낮추고 신뢰도의 문제가 생길 수 있어. 그래서 깃허브의 방식처럼 PR 같은게 있어서 이걸 관리하는 관리자들이 평가하고 추가하는식의 검토 절차가 필요해보여. 이렇게 되면 내 방식대로 수정해서 사용하다가 너무 좋아서 오리지널 덱에 추가할 수도 있고 버전 관리도 쉽지 않을까? 다만, 이렇게된다면 ui나 ux가 다소 복잡해질 가능성이 있어서 이부분에 대한 고려가 필요해보여.

### Q6. Neo-Anki가 카드의 우선순위를 바꾸거나, 긴 카드를 자동으로 분해하거나, 학습 순서를 조정한다면 어느 정도까지 자동으로 해도 괜찮아?

*자동 적용, 적용 전 제안, 변경 이유 설명, 언제든 되돌리기 중 무엇이 필요할까?*

**답변**

적용 전에 제안하고 그 이유를 간략하게라도 설명해주면 충분할 것 같고, 언제든지 이전 상태로 되돌릴 수 있도록 일종의 커밋의 단위로 이걸 관리해도 좋을 것 같아.
