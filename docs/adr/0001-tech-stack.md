## 3. 결정 1. 앱 셸

> 결정할 것: 무엇 위에서 앱을 돌리는가?

### 결정

**데스크톱 앱으로 만든다.** (결정일: 2026-09-20)

### 근거

결정적인 이유는 하나다. **학습 자료를 기기 안에서 분석하려면 데스크톱이 필요하다.**

- 자료 파일과 모델 파일을 직접 다뤄야 한다. 브라우저 저장소 안에서는 용량과 접근에 제약이 크다.
- 자료와 카드 내용을 외부로 보내지 않는다. 외부 API를 쓰면 키 관리, 비용, 프라이버시가 전부 따라온다.
- 제품 방향의 `Local-first`와 `Source-linked learning` 원칙에 정면으로 맞는다.
- 부수 효과로 `.apkg` 파싱이 쉬워진다. zip 해제와 SQLite 읽기가 네이티브에서는 표준 라이브러리 수준이다.

### 이 결정이 감수하는 것

| 감수 | 내용 |
|---|---|
| 모바일 복습 불가 | 인터뷰에서 사용자는 iOS 앱이 유료라 모바일 웹으로 복습했다고 진술했다. 실제 습관 하나를 덮지 못한다 |
| 설치 장벽 | 웹과 달리 다운로드와 설치가 필요하다. 테스터 확보가 그만큼 어렵다 |
| 배포 부담 | OS별 빌드와 서명을 다뤄야 한다 |

첫 번째가 실제 손실이다. 다만 로컬 모델 추론을 모바일에서 돌리는 것은 어차피 무리이므로, 자료 분석을 택한 시점에 따라오는 대가로 본다. 이후 동기화 계층이 생기면 모바일은 가벼운 복습 전용 클라이언트로 분리한다.

### 폐기한 대안. 웹앱

같은 날 웹앱으로 먼저 결정했다가 뒤집었다. 기록을 남긴다.

| | |
|---|---|
| 웹앱의 장점 | 플랫폼 선택을 미룰 수 있고, 모바일에서도 열리고, 설치가 없다 |
| 뒤집은 이유 | 기기 안에서 자료를 분석하기로 하면서 전제가 바뀌었다. 브라우저에서는 모델 파일과 자료 파일을 다루기 어렵다 |
| 다시 검토할 조건 | 자료 분석을 포기하거나, 분석을 임베딩 수준으로만 한정하는 경우. 그 정도는 브라우저에서도 가능하다 |

아무것도 구현하지 않은 상태라 이 전환의 비용은 0이다. 구현 시작 후에는 같은 전환이 훨씬 비싸진다.

## 6. 결정 4. SRS 구현

> 결정할 것: 어떤 SRS를 쓰고, 어떻게 가져오는가?

| 후보 | 형태 | 검토 결과 |
|---|---|---|
| `fsrs-rs` | Rust 크레이트 | **1순위.** Anki 본체가 쓰는 구현으로 알려져 있다. 언어도 맞는다 |
| Anki `rslib` 일부 사용 | Rust | 의존성이 무겁다. fsrs-rs로 충분하면 불필요 |
| 직접 구현 | - | 범위 주의사항에서 배제 대상 |

### 결정

**FSRS를 쓴다.** Rust에서는 `fsrs-rs`. [스파이크 5](../engineering/spike-05-fsrs.md)에서 네 항목을 모두 확인했다.

| 확인 항목 | 결과 |
|---|---|
| 라이선스 | **MIT.** 배포 앱에 제약 없음 |
| Again/Hard/Good/Easy 4등급을 그대로 받는가 | **받는다.** 값이 1/2/3/4로 우리 `review_log.rating` 과 정확히 일치 |
| 덱별 파라미터를 다르게 줄 수 있는가 | **가능하다.** 스케줄러 생성자가 전부 받는다. 인스턴스를 덱별로 만든다 |
| 학습 단계를 누가 관리하는가 | **라이브러리가 관리한다.** 7장의 분담과 일치 |

한 가지 덧붙인다. **테스트에서는 `enable_fuzzing` 을 끈다.** 같은 입력에 다른 결과가 나오면 큐 테스트가 성립하지 않는다.

### 이 스파이크가 스키마에서 찾아낸 것

- `card.srs_step` 이 없으면 학습 단계가 복원되지 않는다 → 추가했다
- `state = 'buried'` 는 보류 전 상태를 지운다 → `buried_until` 기간으로 바꿨다

자세한 내용은 스파이크 보고서에 있다.

### 검증은 Python으로 했다

Rust 툴체인이 없어 같은 조직의 Python 구현으로 확인했다. 알고리즘과 API 모양이 같아 답은 그대로 옮겨지지만, **`fsrs-rs` 의 실제 시그니처와 라이선스는 Rust 환경이 준비되면 재확인한다.**

## 7. 결정 5. SRS와 Addiem 큐의 책임 경계

이 ADR에서 가장 중요한 결정이다. 기술 스파이크 6번에 해당하며, 이 경계가 흐리면 MVP 범위 6.8의 반복 루프 방지가 SRS 동작과 충돌한다.

**상태: 확인됨, 승인 대기.** [큐 명세](../engineering/study-queue-spec.md)를 쓰면서 정했고,
[스파이크 5](../engineering/spike-05-fsrs.md)에서 FSRS가 이 분담을 실제로 허용함을 확인했다.
작성자의 최종 승인만 남았다.

### 경계 한 줄 요약

> **SRS 라이브러리는 카드 한 장의 다음 일정만 계산한다.
> 오늘 무엇을 어떤 순서로 보여줄지는 전부 Addiem 큐가 결정한다.**

### 분담

| 동작 | 담당 | 근거 |
|---|---|---|
| 카드별 다음 복습 간격 계산 | **SRS** | 검증된 알고리즘을 재구현하지 않는다 |
| 난이도 및 안정성 같은 카드 내부 상태 갱신 | **SRS** | 같음 |
| Again 직후 같은 세션 내 재등장 (학습 단계) | **SRS** | 학습 단계는 알고리즘의 일부다 |
| 하루 신규 카드 상한 적용 | **큐** | 덱 설정이고 SRS가 모르는 개념이다 |
| 목표일 기반 신규 카드 분배량 산정 | **큐** | Addiem 고유 기능이다 |
| 오늘 큐에 넣을 카드 선택 | **큐** | SRS는 카드 한 장만 본다 |
| 중요도를 반영한 정렬 | **큐** | SRS에 중요도 개념이 없다 |
| 같은 세션 2회 Again 시 보류 판정 | **큐** | 세션은 큐의 개념이다 |
| 보류 카드의 SRS 상태 처리 | **큐가 결정, SRS는 모름** | 아래 참고 |
| 보류 카드의 세션 말 재제시 | **큐** | |
| 밀린 복습 카드의 처리 순서 | **큐** | 상한과 정렬 모두 큐 소관 |
| 여러 덱을 합쳐 학습할 때의 분량 배분 | **큐** | 예산 덱 단위로 계산한다 |

### 보류 카드의 SRS 상태

> 1회차 Again은 스케줄러에 넘긴다. 보류를 유발한 **2회차 Again은 넘기지 않는다.**
> 두 번 모두 `review_log` 에 기록하고, `fed_to_scheduler` 로 구분한다.

| 대안 | 문제 |
|---|---|
| 둘 다 넘긴다 | 카드가 내일 again due로 올라와 또 막힌다. 루프 방지가 하루짜리가 된다 |
| 둘 다 안 넘긴다 | 실패가 스케줄러에서 사라져 난이도 추정이 낙관적이 된다 |
| **1회차만 넘긴다** | 실패는 반영되고 재등장 시점은 큐가 통제한다 |

### 이 경계가 깨지는 상황

| 상황 | 대응 |
|---|---|
| SRS 라이브러리가 학습 단계를 호출자에게 맡긴다 | **해당 없음.** 스파이크 5에서 라이브러리가 관리함을 확인했다 |
| SRS가 "오늘 볼 카드 목록"을 반환하는 API만 제공한다 | **해당 없음.** `review_card(카드, 평가)` 로 카드 한 장만 다룬다 |
| SRS가 내부에 자체 덱/상한 개념을 갖는다 | 사용하지 않는다. 큐의 결정과 충돌한다 |
| 덱별로 다른 스케줄러 파라미터를 못 준다 | MVP에서는 감수한다. 덱별 파라미터는 Must가 아니다 |

## 8. 결정 6. `.apkg` 파싱 방식

[스파이크 1](../engineering/spike-01-apkg-parsing.md)에서 실제 컬렉션을 열어 측정했다. 아래는 추측이 아니라 실측 결과다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 파싱 라이브러리 | **직접 구현.** `zip` + `zstd` + `rusqlite` + protobuf 수동 파싱 | 구조가 단순해 전용 파서 크레이트가 필요 없다 |
| 지원할 collection 포맷 | `collection.anki21b` (zstd 압축, 스키마 ver 18) | 실측 파일이 이 포맷이다 |
| 구버전 포맷 | `TODO` — 별도 샘플로 확인 | 실측 파일의 `collection.anki2`는 스텁 51KB였다 |
| 미디어 매핑 처리 | `media` 항목을 zstd 해제 후 protobuf 파싱. 미디어 파일도 개별 zstd | 이름·인덱스 매핑이라 단순하다 |
| 미지원 요소 탐지 방식 | **템플릿이 쓰는 기능으로 판정.** 노트타입 이름으로 판정하지 않는다 | 실측에서 75%가 커스텀 노트타입이었다 |
| 복습 이력 이전 범위 | 데이터는 온전하다 (revlog 7,745건). 매핑 범위는 7장 확정 후 | 기술적 가능성은 확인됨 |

### 반드시 지켜야 할 것

스파이크에서 발견한 함정이다. 놓치면 조용히 틀린 결과가 나온다.

| 항목 | 내용 |
|---|---|
| zip 안이 다시 zstd다 | zip은 `stored`(무압축)이고 실제 압축은 각 항목 안에 있다. zip만 풀고 SQLite로 열면 실패한다 |
| `collection.anki2`는 스텁이다 | 구버전 경고용 빈 껍데기다. 진짜 데이터는 `collection.anki21b`에 있다 |
| `unicase` 콜레이션 등록 필수 | 없으면 `decks`, `notetypes` 쿼리가 실패한다. `create_collation`으로 등록한다 |
| 필터 덱은 `odid`를 본다 | `cards.odid`가 0이 아니면 그것이 실제 덱이다. 실측에서 455장이 해당했다 |
| 덱 이름 구분자는 `` | `::`가 아니라 unit separator다 |
