# 성격별로 묶기 (`ai_regroup`) Harness

## 문서 상태

- 버전: v0.1
- 상태: **1–6절 확정, 코드 반영함, 첫 측정을 마쳤다 (2026-11-15, `gpt-6-luna` 높음).** 묶음은 기대와 모두 맞았고, 답 누설 검사가 좋은 질문을 잘못 비우는 일이 있었다 (6.8). 화면은 바뀌지 않아 따로 보지 않았다. 지표의 기준 수치는 아직 정하지 않았다
- 화면: 카드 점검 › 나누기 제안 창의 [비슷한 내용끼리 나누기] (`src/screens/Quality.tsx` `SplitModal`). DECISIONS 와 코드에서는 "성격별로 묶기"라 부른다
- 코드: `src-tauri/src/ai.rs` 의 "성격별로 묶기 (프롬프트 · 검사)" 구간과 `ai_regroup` · `regroup_blocking` · `parse_cited`, `quality.rs` 의 `answer_items` · `strip_marker` · `split_apply`
- 관련: [README](README.md), [DECISIONS](../../DECISIONS-PENDING-REVIEW.md) I66 · I74 · I76 · I77 · L5 · L7 · L9 · R18–R20 · R26

## 0. 다시 쓰기 전의 상태 (2026-11-15 까지의 코드)

카드 점검에서 답 항목이 많은 카드에 [나누기]를 누르면 나누기 제안 창이 열린다. 처음에는 규칙 분할 제안(번호 · 줄 단위, I66)이 보이고, [비슷한 내용끼리 나누기]를 고르면 그 카드 한 장을 ChatGPT 로 보낸다.

- **보내는 것** (I74 · R18): 질문 글자와 번호 붙인 답 항목 글자 (HTML · 그림 · `[sound:]` 를 뺀 규칙 분할과 같은 글자), 그리고 카드에 연결된 자료 구간 중 확인 목록에서 남긴 것 (직접 > 자동, 3개까지, 구간 600자). 항목이 3개 미만이면 보내지 않고, 60항목 · 6,000자를 넘으면 보내지 않는다.
- **받는 것**: `{"cards": [{"front", "items": [번호…], "segments": [번호…]}]}`. `segments` 는 구간을 보냈을 때만 스키마에 있다. 모델은 항목 **번호**만 내고, 카드의 답은 코드가 원래 항목 글자를 이어 붙여 만든다.
- **코드가 확인하는 것** (`parse_regroup`, `parse_cited`): JSON 인가, 카드 2–8장, `front` 가 비지 않고 200자 이내, 카드마다 항목이 하나 이상, 모든 항목 번호가 정확히 한 번 (없는 번호 · 겹침 · 빠짐 없음), 구간 번호가 보낸 범위 안. 하나라도 어긋나면 `BadOutput` 이고 한 조각도 쓰지 않는다 (I77).
- **코드가 확인하지 않는 것**:
  - `front` 에 그 카드의 답(항목 글자)이 그대로 들어갔는가. 지시문에도 "답을 드러내지 말라"는 말이 없다.
  - 두 카드의 `front` 가 같은가.
  - 한 카드 안의 항목 순서. 모델이 쓴 번호 순서대로 답을 이어 붙인다 (`[4, 1]` 이면 4번이 먼저).
  - 묶음이 실제로 성격이 같은 항목끼리인가, `front` 가 그 묶음을 가리키는가, 같은 카드를 다시 묶으면 같은 묶음이 나오는가.
  - `front` 에 자료 구간의 내용이 섞였는가. "구간 내용을 답에 더하지 마세요"는 답이 번호라 구조로 지켜지지만, 질문에 대해서는 말이 없다.
- **실패하면**: 화면이 규칙 제안을 그대로 두고 "ChatGPT 답을 쓰지 못했어요 · 형식이 맞지 않아 쓰지 않았어요. 카드는 그대로예요."와 [다시 나누기]를 보인다. 실패 기록(`ai::log_failure`)은 남기지 않는다.
- **승인**: 화면의 제안은 고칠 수 있는 목록이다 (질문 · 답 · 빼기 · 더하기). 카드를 바꾸는 것은 사용자가 누른 `quality::split_apply` 뿐이고, 그것은 화면이 보낸 글자를 받는다. ChatGPT 출력은 그 앞에서 제안일 뿐이다.
- **측정**: 단위 테스트는 손으로 쓴 출력과 가짜 응답으로 `parse_regroup` · `parse_cited` · 보내는 글만 검사한다. 실제 ChatGPT 출력의 묶음 품질 · 질문 품질 · 실행 간 편차는 잰 적이 없고, 평가셋도 없다.

사전 검토대로 구조는 다섯 작업 가운데 가장 탄탄하다. 모델은 답 글자를 고칠 수 없고, 모든 항목이 정확히 한 번 들어가는 것은 코드가 강제한다. 모델이 쓰는 자유 글은 `front` 하나이고, 남은 빈틈은 대부분 거기에 있다.

### 1.2 목표

답 항목이 많아 한 번에 외우기 어려운 카드를, 성격이 같은 항목끼리 2–8장으로 나누는 제안을 낸다. 나눈 카드마다 그 묶음만 묻는 질문이 있고, 답은 원래 카드의 글자 그대로다.

### 1.3 맥락

- 대상: 카드 점검에서 답 항목이 많다고 표시된 카드 (I66). ChatGPT 를 연결한 사람만 쓴다 (L1).
- 왜: 규칙 분할은 번호 순서로 끊는다. "조직 문화의 특성 10가지"를 1–5번 · 6–10번으로 나누면 한 장 안의 항목이 서로 상관없어 외우기 어렵다. 성격이 같은 것끼리 묶어야 질문이 그 묶음을 가리킬 수 있다.
- 결과는 제안이다. 사용자가 읽고 고친 뒤 승인해야 카드가 생긴다 (L5).

### 1.4 제약

**답**

- 모델은 항목 번호만 낸다. 답 글자는 코드가 원래 항목에서 가져온다 (I74 그대로).
- 한 카드 안의 항목은 원래 순서대로 잇는다. 모델이 쓴 번호 순서를 따르지 않는다. 과정 · 단계를 적은 카드에서 순서가 뒤집히지 않게 하려는 것이고, 코드가 정할 수 있는 것은 모델에게 맡기지 않는다는 원칙이다. 카드끼리의 순서는 모델이 낸 순서 그대로다.
- 모든 항목이 정확히 한 번 들어가고, 카드는 2–8장이다. 어긋나면 한 조각도 쓰지 않는다 (I77 · L5 그대로).

**질문 (`front`)**

- 원래 질문의 주제와 그 묶음의 성격이 드러나게, 원래 질문과 같은 언어로 쓴다 (지금과 같다).
- 그 카드의 답 항목을 질문에 쓰지 않는다. 지시문에 새로 적고, 코드가 글자로 확인한다. 견줄 때는 글자와 숫자만 본다 (띄어쓰기 · 문장 부호 · 대소문자 무시, 채점 보조 GR-H-10 과 같다). 2자 미만인 항목과 원래 질문에 이미 들어 있는 항목은 보지 않는다.
- 두 카드의 질문이 같으면 (같은 견줌으로) 구별되지 않는 것으로 본다.
- 이 두 검사에 걸리면 그 질문만 비우고 나머지 묶음은 쓴다 (1.8 갈림길 1). 사용자가 빈 질문을 채운다.
- 자료 구간의 내용을 질문에 섞지 않는다. 코드로 확인할 수 없어 지시문에만 두고, 평가셋에는 구간이 없으므로 재지 않는다 (6절에 적는다).

**그대로 두는 것**

- 보내는 글과 상한 (I74 · R18), 첫 확인 목록 (R19), 연결 · 모델 고르기 · 형식 지정 (I76), 실패 처리와 규칙 제안으로 돌아가기 (I77), 30초 안내 (L9), 멈춤 (R26), 고친 제안을 닫을 때 묻기 (L7).
- 형식 오류 뒤에 자동으로 다시 보내지 않는다. 사용자가 [다시 나누기]를 누른다.

### 1.5 범위

포함: 묶음과 질문 제안, 답 글자 · 순서 보존, 질문의 답 누설 · 겹침 검사, 근거 구간 칩, 실패 기록, 평가셋과 평가를 돌리는 길.

제외:

- 항목 글자를 다듬거나 합치는 제안 (I74: 번호만 받는다)
- 항목을 두 카드에 겹쳐 넣기, 항목을 빼기
- 묶음 이름을 따로 받는 것 (질문이 그 역할을 한다)
- 화면 바꾸기. 걸린 질문을 처리하는 방식은 지금 화면이 이미 그리는 상태 안에서 고른다 (갈림길 1)
- 형식 오류 뒤의 자동 재요청

### 1.6 출력 형식과 평가 지표

명령이 화면에 돌려주는 것은 지금과 같다 (`quality::SplitProposal`, `kind: "nature"`).

```text
parts:    [{ front  질문 (모델이 쓴 글. 검사에 걸리면 빈 글)
             back   원래 항목 글자를 원래 순서로, 줄바꿈으로 이음 }]   2–8장
why:      "왜?" 한 줄. 걸린 규칙 + ChatGPT 가 나눈 장수 (+ 비운 질문이 있으면 그 수)
sent:     보낸 구간
evidence: 보낸 구간 가운데 인용한 것 (처음 나온 순서)
```

평가셋은 새로 만든다 (갈림길 2). 지표는 모두 코드가 결과 줄에서 센다. 기준 수치는 첫 측정 뒤 정한다.

| 지표 | 잇는 기준 | 셈 |
|---|---|---|
| 잘못 합친 비율 | RG-SC-05 | 모델이 한 카드에 넣은 항목 짝 가운데 기대 묶음에서는 다른 묶음인 짝 |
| 잘못 가른 비율 | RG-SC-05 | 기대 묶음에서 같은 묶음인 항목 짝 가운데 모델이 다른 카드로 가른 짝 |
| 묶음 일치율 | RG-SC-06 | 세 번 모두 같은 묶음이 나온 카드 ÷ 카드 (카드 순서 · 질문 글은 보지 않는다) |
| 짝 일치율 | RG-SC-06 | 세 번 사이에서 "같은 카드인가"가 같게 나온 항목 짝의 비율. 묶음 일치율이 0/1 이라 놓치는 작은 흔들림을 본다 |
| 답 누설 비율 | RG-SC-03 | 질문 가운데 RG-SC-03 의 검사에 걸린 것 |
| 질문 겹침 비율 | RG-SC-04 | 결과 가운데 같은 질문이 둘 이상인 것 |
| 형식 오류율 | — | 전체 호출 가운데 `BadOutput` |

짝으로 세는 까닭: 묶음 번호는 실행마다 달라도 되고, 묶음이 하나만 어긋나도 카드 전체를 틀렸다고 하면 정도를 모른다. 짝으로 세면 합친 쪽과 가른 쪽의 잘못을 따로 볼 수 있다 (채점 보조 첫 측정의 교훈: 한쪽 지표만 있으면 치우침을 모른다).

| 선택지 | 하는 일 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **A. 그 질문만 비운다 (추천)** | 걸린 카드의 질문을 빈칸으로 두고 나머지는 쓴다. "왜?" 줄에 "질문 N개는 답이 보여 비웠어요"를 붙인다. 겹친 질문은 두 번째부터 비운다 | 묶음은 살린다. 화면은 이미 빈 질문을 "질문을 써 주세요"로 그리고, 질문을 쓰기 전에는 그 카드를 나누지 않으므로 화면 코드를 바꾸지 않는다. 채점 보조의 "그 기준만 보류로 내림"과 같은 방식 | 사용자가 질문을 직접 써야 한다 |
| B. 전부 버린다 | `BadOutput`. 규칙 제안 + [다시 나누기] (I77 방식) | 지금 검사들과 한 가지 규칙 | 묶음은 좋은데 질문 하나 때문에 사용량을 쓴 결과를 다 버린다 |
| C. 검사하지 않는다 | 평가셋에서 세기만 한다 | 코드 변경 없음 | 답이 보이는 질문이 그대로 카드가 될 수 있다 (사용자가 놓치면) |

**갈림길 2. 평가셋을 어떻게 만들고 "좋은 묶음"을 무엇으로 재는가**

평가셋은 필요하다고 본다. 묶음 품질 · 질문 품질 · 재현성은 실제 출력으로만 확인되고, 지금은 한 번도 잰 적이 없다.

| 선택지 | 하는 일 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **A. 손으로 쓴 카드 + 기대 묶음 (추천)** | `src-tauri/tests/fixtures/regroup-dev.jsonl` 에 카드 12장쯤을 이 세션이 쓴다 (질문, 항목, 기대 묶음). 측정 전에 사용자가 기대 묶음을 읽고 고친다. 짝 지표는 코드가 세고, 질문은 사람이 읽는다 | 지표를 코드가 세고 다시 잴 수 있다. 짝으로 세므로 두 방향의 잘못을 따로 본다 | 기대 묶음이 하나뿐이라, 다르지만 그럴듯한 묶음도 틀림으로 센다. 어긋난 카드는 사람이 다시 본다 |
| B. 기대 묶음 없이 사람이 읽는다 | 카드만 두고, 결과를 사람이 모두 읽어 좋음 · 나쁨을 적는다 | 정답이 여럿인 묶음을 공정하게 본다 | 다시 잴 때마다 사람이 다 읽어야 한다. 수치가 사람마다 다르다 |
| C. 사용자의 실제 덱에서 뽑는다 | 사용자가 항목이 많은 카드를 내보내 평가셋으로 쓴다 | 실제 쓰임과 같다 | 개인 학습 자료가 저장소에 들어간다. 기대 묶음은 어차피 사람이 써야 한다 |

A 를 고르면 12장은 이렇게 섞는다: 성격이 뚜렷이 나뉘는 목록 (6장쯤), 과정 · 단계라 순서가 중요한 목록 (2장), 항목에 원래 질문의 낱말이 든 목록 (누설 검사의 예외를 보려고, 2장), 여러 묶음이 다 그럴듯한 목록 (재현성만 보려고 기대 묶음을 두지 않음, 2장). 내용은 교과서 수준의 일반 지식으로 쓰고 출처를 인용하지 않는다.
카드마다 3번 돌리므로 요청은 36회 안팎이다.

## 2. Skill

모델에게 맡기는 일은 하나다: 번호 붙은 항목을 묶고, 묶음마다 질문을 쓴다. 지시문은 하나이고, 자료 구간을 보낼 때만 한 줄을 덧붙인다.

| | 묶기 |
|---|---|
| 하는 일 | 항목을 성격이 같은 것끼리 2–8묶음으로 나누고, 묶음마다 그 묶음만 묻는 질문을 쓴다 |
| 언제 | 나누기 제안 창에서 [비슷한 내용끼리 나누기]를 고르거나 [다시 나누기]를 누를 때 |
| 받는 것 | 질문, 번호 붙은 답 항목, (있으면) 번호 붙은 자료 구간 |
| 내는 것 | `{"cards": [{"front", "items": [번호…], "segments": [번호…]}]}` (`segments` 는 구간이 있을 때만) |
| 하지 않는 것 | 항목 글자 고치기 · 더하기 · 빼기, 카드 안 항목의 순서 정하기, 질문에 답 쓰기 |

### 2.1 지시문

```text
암기 카드 한 장을 더 작은 카드로 나누는 일을 도와요. 사용자가 보낸 질문과 번호 붙은 답 항목을 보고, 성격(종류)이 같은 항목끼리 2~8장의 카드로 묶으세요.
- 모든 항목 번호를 정확히 한 번씩, 어느 한 카드에 넣으세요. 항목 글자는 고치지 말고 번호만 쓰세요.
- 카드마다 front 에 그 묶음만 묻는 짧은 질문을 쓰세요. 원래 질문의 주제와 묶음의 성격이 드러나게, 원래 질문과 같은 언어로.
- front 에 그 카드의 답 항목을 쓰지 마세요. 질문만 읽고 답이 보이면 안 돼요. 카드마다 front 가 달라야 해요.
- 답은 {"cards": [{"front": 질문, "items": [번호, …]}]} 모양의 JSON 하나만.

예시
질문: 컴퓨터의 주요 장치를 쓰시오.
답 항목:
1. CPU
2. 키보드
3. 모니터
4. 마우스
5. SSD
6. 프린터
→ {"cards": [{"front": "컴퓨터의 주요 장치 중 처리하거나 저장하는 장치는?", "items": [1, 5]}, {"front": "컴퓨터의 주요 장치 중 입력 장치는?", "items": [2, 4]}, {"front": "컴퓨터의 주요 장치 중 출력 장치는?", "items": [3, 6]}]}
```

자료 구간을 보낼 때 덧붙이는 줄:

```text
- 번호 붙은 자료 구간도 보내요. 묶음과 질문을 정할 때 참고하고, 카드마다 참고한 구간 번호를 "segments": [번호, …] 에 쓰세요 (없으면 빈 배열). front 에는 구간에만 있는 내용을 더하지 마세요.
```

지금과 다른 점:

- "front 에 답 항목을 쓰지 마세요 · front 가 달라야 해요" 줄을 더했다 (RG-SC-03 · 04). 코드가 글자로 확인하지만(5.3), 걸리면 사용자가 질문을 써야 하므로 처음부터 덜 걸리게 지시한다.
- 예시 한 쌍을 더했다. 6절 평가셋에 없는 카드다.
- 구간 줄의 "구간 내용을 답에 더하지는 마세요"를 "front 에는 구간에만 있는 내용을 더하지 마세요"로 바꿨다. 답은 번호라 이미 구조로 지켜지고, 지켜지지 않던 쪽은 질문이다 (R18).

### 2.2 출력 스키마

지금과 같다.

```json
{ "type": "object", "additionalProperties": false, "required": ["cards"],
  "properties": { "cards": { "type": "array", "items": {
    "type": "object", "additionalProperties": false, "required": ["front", "items", "segments"],
    "properties": {
      "front": { "type": "string" },
      "items": { "type": "array", "items": { "type": "integer" } },
      "segments": { "type": "array", "items": { "type": "integer" } } } } } } }
```

`segments` 는 구간을 보낼 때만 넣는다 (`regroup_schema(segments)`). 개수 · 길이 제한(`minItems` 등)은 strict 스키마가 받지 않을 수 있어 파서가 확인한다.
답 글자 · 항목 순서 · 장수를 낼 칸이 없다. 모델이 낼 수 있는 것은 번호와 질문 글뿐이다.

### 2.3 품질 점검

| 조건 | 묶기 |
|---|---|
| 단일 기능 | 통과. 묶음과 질문만 낸다 (이유 · 총평 없음) |
| 명확한 설명 | 통과. 첫 줄이 무엇을 받아 무엇을 하는지 말한다 |
| 범위 명시 | 통과. 장수, 모든 항목 한 번, 글자를 고치지 말 것, 질문에 답을 쓰지 말 것 |
| 예시 포함 | 통과 (이번에 더함). 입출력 한 쌍 |
| 확인 가능 | 아래 표 |

### 2.4 지시문의 규칙을 무엇으로 확인하는가

| 규칙 | 확인 |
|---|---|
| 2–8장 | 코드 (RG-H-05) |
| 모든 항목 번호를 정확히 한 번 | 코드 (RG-H-07) |
| 항목 글자를 고치지 않는다 | 구조 (번호만 받는다) |
| 그 묶음만 묻는 짧은 질문, 주제와 성격이 드러나게 | 길이는 코드 (RG-H-06). 뜻은 사람 (6.5) |
| 원래 질문과 같은 언어로 | 사람 (6.5) |
| 성격이 같은 항목끼리 | 평가셋 (잘못 합친 · 잘못 가른 비율) |
| front 에 답 항목을 쓰지 않는다 | 글자 그대로는 코드 (RG-H-10). 바꿔 말한 것은 사람 (6.5) |
| front 가 서로 다르다 | 글자 그대로는 코드 (RG-H-11). 뜻이 겹치는 것은 사람 (6.5) |
| segments 는 보낸 번호 | 코드 (RG-H-08) |
| front 에 구간에만 있는 내용을 더하지 않는다 | 재지 않는다 (평가셋에 구간이 없다, 6.6) |

## 3. Subagent

여기서 Subagent 는 **ChatGPT 호출 한 번**이다. 묶기는 호출이 하나다.

### 3.1 경계

| 경계 | 묶기 호출 |
|---|---|
| 입력 형식 | 질문, 번호 붙은 답 항목, (있으면) 번호 붙은 자료 구간 |
| 출력 형식 | 2.2 의 스키마 |
| 도구 권한 | 없음 |
| 독립 컨텍스트 | 새 대화. 규칙 분할 제안, 지난 묶기 결과, 다른 카드를 받지 않는다 |

### 3.2 입력 형식

지시문과 따로 가는 사용자 입력 하나다 (`ai::request_body` 의 `instructions` / `input`). 지금과 같다.

```text
질문: <질문>
답 항목:
1. <항목>
2. <항목>
자료 구간:
[1] <구간 글>
```

- 질문과 항목은 규칙 분할과 같은 글자다: HTML · 그림 · `[sound:]` 를 뺀 화면 글자 (`quality::suggest`), 항목은 `quality::answer_items` 로 나누고 앞 표시(①, 1.)를 뗀 것 (`regroup_items`). 항목 표시가 없으면 줄이 항목이다.
- 항목 3개 미만이면 보내지 않는다. 질문 + 항목이 60항목 · 6,000자를 넘으면 보내지 않고 규칙으로 나누라고 안내한다 (자르지 않는다. 잘린 항목은 묶을 수 없다).
- 구간은 그 카드에 연결된 것 가운데 확인 목록에서 남긴 것, 3개까지, 구간 600자 (`rag::linked_segments` · `rag::sent_of`). 구간이 없으면 "자료 구간:" 줄도 없고 구간 지시 줄도 붙이지 않는다.

### 3.3 출력 형식

- 2.2 의 스키마를 `json_schema`(strict)로 요청한다. 형식 지정을 받지 않는 모델이면 형식 없이 다시 보내고 (I76), 어느 쪽이든 받은 글은 5절의 검사를 지난다.
- 모델은 항목과 구간을 번호로만 가리킨다. 화면에 보이는 답 글자는 코드가 가진 항목 글자, 근거 칩은 코드가 가진 구간이다.

### 3.4 도구 권한

- 모델에게 도구를 주지 않는다. 요청은 `store: false` 다.
- 모델은 카드를 바꿀 수 없다. 출력은 제안 글자일 뿐이고, 카드를 만드는 것은 사용자가 화면에서 고치고 승인한 글자로 부르는 `quality::split_apply` 다.

### 3.5 독립 컨텍스트

- 앞 대화 없이 지시문과 입력 하나로 시작한다. [다시 나누기]도 새 대화다.
- 보내지 않는 것은 I74 그대로다: 덱 이름, 다른 카드, 복습 기록, 일정, 원자료 파일, 그림. 구간은 글만 가고 자료 이름 · 쪽은 가지 않는다.

## 4. Workflow

### 4.1 흐름

```text
[나누기] (카드 점검)
  규칙 분할 제안을 보인다 (quality::suggest · 아무것도 보내지 않는다)

[비슷한 내용끼리 나누기]
  연결이 없다 ──────────────→ 연결 창 (L2). 돌아오면 규칙 제안. 저절로 보내지 않는다
  받은 결과가 있다 ─────────→ 그 결과를 다시 보인다 (보내지 않는다)
  처음 보내기면 확인 (L4 · 구간이 있으면 목록, R19)
  ① 보내기 전 검사 (코드)
       항목 3개 미만 · 60항목 · 6,000자 초과 ──→ 오류 (보내지 않음)
  ② 묶기 호출 ──→ 검사 ─ 실패 ─→ 결과 없음 (형식 오류). 규칙 제안 + [다시 나누기]
  ③ 고침 (코드): 카드 안 항목을 원래 순서로, 답이 보이거나 겹치는 질문은 비운다
  ④ 결과 보이기: 고칠 수 있는 제안 목록 + "왜?" 줄 + 근거 칩

[N장으로 나누기]  카드를 바꾸는 것은 이것뿐 (split_apply, 고친 글자로). 질문이 빈 카드는 나누지 않는다
```

### 4.2 단계 사이에 넘기는 것

| 단계 | 받는 것 | 넘기는 것 |
|---|---|---|
| ① 보내기 전 | 카드 id, 남긴 구간 id | 규칙 제안 (질문 · 답 줄 · 걸린 규칙), 항목 글자 목록, 보낼 구간 |
| ② 묶기 | 질문, 항목, 구간 | 묶음 (질문 · 항목 번호), 인용한 구간 번호 |
| ③ 고침 | ②의 묶음, 원래 질문, 항목 | 질문 (비웠을 수 있음) · 원래 순서의 항목 번호 |
| ④ 결과 | ①–③ | 1.6 의 출력 |

①–③은 한 명령(`ai_regroup`) 안에서 차례로 돈다. 화면은 지금처럼 보내는 중 → 결과 / 오류만 안다.

### 4.3 종료 상태

| 상태 | 언제 | 화면 |
|---|---|---|
| 제안 | 검사를 지났고 비운 질문이 없다 | ChatGPT 제안 목록 (지금과 같다) |
| 질문을 써야 하는 제안 | 검사를 지났고 비운 질문이 있다 | 같은 목록. 빈 질문은 "질문을 써 주세요"로 보이고 "왜?" 줄에 "답이 드러나거나 겹치는 질문 N개를 비웠어요"가 붙는다. 그 카드는 질문을 쓰기 전에는 나누는 수에 들지 않는다 |
| 결과 없음 (형식 오류) | ②의 검사에 걸렸다 | 규칙 제안 + "ChatGPT 답을 쓰지 못했어요" + [다시 나누기] (I77). 까닭은 `ai-errors.log` 에 |
| 결과 없음 (보내지 못함) | 미연결 · 한도 · 오프라인 · 잠시 쓸 수 없음 · 다시 로그인 · 너무 긺 | 지금의 오류 문구 그대로 |
| 멈춤 | [취소] · [규칙으로 나누기] · 창을 닫음 | 규칙 제안으로 돌아간다. 토스트 "요청을 멈췄어요" (R26) |

어느 상태에서도 규칙 제안으로 돌아가 나눌 수 있다.

### 4.4 다시 하기와 횟수

- 형식 오류 뒤에 자동으로 다시 보내지 않는다. 사용자가 [다시 나누기]를 누른다.
- 연결 층의 다시 하기는 그대로다: 401 이면 토큰을 한 번 새로 받아 다시, 형식 지정을 받지 않으면 형식 없이 한 번 다시 (I76 · I77).
- "이번 달 보낸 수"는 요청마다 하나씩 오른다.

## 5. Hook

모델의 판단과 상관없이 코드가 **항상** 돌리는 검사다. 걸렸을 때 하는 일은 셋 중 하나다.

- **보내지 않음**: 요청 전에 오류로 끝낸다.
- **전부 버림**: `AiError::BadOutput` 을 내고 결과를 한 조각도 쓰지 않는다 (I77).
- **고침**: 값을 바꾸고 계속한다.

### 6.3 평가를 돌리는 방법

실제 ChatGPT 출력은 **앱 안에서 로그인한 계정으로** 잰다 (채점 보조 6.3 과 같은 방식).

- debug 빌드에서만 듣는 환경 변수로 시작한다: `ADDIEM_REGROUP_EVAL=<결과 파일>` 을 주고 앱을 띄우면 돈다. `ADDIEM_REGROUP_EVAL_SET=<jsonl>` (없으면 `src-tauri/tests/fixtures/regroup-dev.jsonl`), `ADDIEM_REGROUP_EVAL_LIMIT=n` (앞 n장). 릴리스 빌드는 듣지 않는다.
- 평가셋은 `regroup-dev.jsonl` 12장이다 (`id` · `kind` · `question` · `items` · `groups`). `groups` 는 기대 묶음(1부터 센 항목 번호)이고, `kind` 가 open 이면 없다.
- 카드마다 앱과 같은 길(`regroup`: 보내기 전 검사 → 묶기 → 검사 → 고침)로 3번 돈다. 구간은 보내지 않는다. DB 에 쓰지 않는다.
- 결과는 한 줄에 호출 한 번씩 JSON 으로 남긴다: 실행 시각, 모델 이름, 지시문 해시, 카드 id, 회차, 묶음(원래 순서의 번호), 모델이 쓴 질문, 비운 까닭(`leak` · `same` · 없음), 또는 오류 종류. **시각 · 모델 · 해시는 코드가 적는다.**
- 지표는 결과 줄에서 코드가 세어 `<결과 파일>.summary.txt` 와 stderr 에 쓴다 (`regroup_eval_summary`).
- 한도 · 오프라인 · 로그인 문제면 거기서 멈추고 그때까지의 결과를 남긴다. 요청은 36회 안팎이고 "이번 달 보낸 수"에 들어간다.
- 가짜 응답(`ADDIEM_AI_FAKE=ok`)을 함께 주면 계정 없이 길만 끝까지 돌아 본다. 지표 값에는 뜻이 없다.

### 6.4 지표와 기준 수치

| 지표 | 성공 기준 | 셈 | 기준 수치 | 측정값 |
|---|---|---|---|---|

기준 수치는 첫 측정값을 보고 사용자가 정한다. 정한 뒤에는 지시문이나 검사를 바꿀 때마다 다시 재서 이 표에 날짜 · 모델과 함께 적는다.
기대 묶음과 다른 결과를 바로 틀렸다고 하지 않는다. 어긋난 카드는 결과 파일에서 묶음과 질문을 사람이 읽고, 그럴듯한 다른 묶음이면 6.8 에 적는다.

### 6.5 사람이 확인하는 것

화면 (debug 빌드). 아직 보지 않았다.

- [ ] 제안: ChatGPT 제안 목록이 보이고, 카드 안 항목이 원래 카드의 순서대로다
- [ ] 질문을 써야 하는 제안: 비운 질문이 "질문을 써 주세요"로 보이고, "왜?" 줄에 비운 수가 있고, 질문을 쓰기 전에는 [N장으로 나누기]의 수에 들지 않는다 (가짜 응답의 질문은 걸리지 않으므로 실제 연결에서 걸린 카드로 본다)
- [ ] 결과 없음 (형식 오류, `ADDIEM_AI_FAKE=malformed`): 규칙 제안 + "ChatGPT 답을 쓰지 못했어요" + [다시 나누기]. `ai-errors.log` 에 `ai_regroup` 한 줄이 남는다
- [ ] 근거 칩 (자료를 붙인 덱에서): 인용한 구간만 칩으로 보인다
- [ ] 실제 연결에서 한 번

평가 결과 (첫 측정 뒤, 결과 파일의 질문을 읽는다):

- [ ] 질문만 읽고 어느 묶음을 답해야 하는지 아는가
- [ ] 바꿔 말해 답을 드러낸 질문이 있는가 (예: 항목 "고등어 · 상어"인 카드의 질문이 "물고기 이름은?"이 아니라 "등 푸른 생선과 연골어류는?")
- [ ] 뜻이 겹쳐 서로 헷갈리는 질문이 있는가
- [ ] 원래 질문과 같은 언어인가

### 6.6 이 평가셋이 재지 못하는 것

| 재지 못하는 것 | 까닭 | 지금의 확인 |
|---|---|---|
| 자료 구간을 함께 보낼 때 | 평가셋에 구간이 없다. 구간은 DB 의 자료에 묶여 있다 | 번호 범위는 단위 테스트. 묶음 · 질문에 구간이 끼치는 영향은 재지 않는다 |
| 항목이 많은 카드 (20개 이상) | 평가셋 카드는 4–10항목이다 | 60항목 상한은 단위 테스트 |
| 한국어가 아닌 카드 | 카드가 모두 한국어다 | 재지 않는다 |
| 사용자가 실제로 만든 카드 | 손으로 쓴 교과서 수준의 카드다 | 실제 연결에서 한 번 보는 것 (6.5) |

채워야 할 때 항목을 더한다. 지금은 더하지 않는다.
