## 0. 다시 쓰기 전의 상태 (2026-11-15 까지의 코드)

선택형 카드를 쓰는 편집기에서 정답에 체크하면 보기 목록 아래에 [오답 보기 N개 제안 받기]가 켜진다. ChatGPT 가 연결돼 있을 때만 보인다 (Q8 · Q40).

- **몇 개** (Q37): 내용 있는 보기 1–3개면 4지선다까지(4 − 그 수), 4–5개면 1개, 6개면 받지 않는다. 화면이 센다 (`wantedDistractors`). 명령은 5개를 넘지 않게만 자른다.
- **보내는 것** (Q38 · Q42 · Q44): 질문(편집기 HTML → 화면 글자, 600자), 정답 보기(200자씩, 여럿이면 모두), 이미 쓴 오답(사용자가 ✕ 로 뺄 수 있다), 이 창에서 앞서 받았지만 보기 칸에 없는 제안(피할 보기), 만들 오답 수. 덱 이름 · 다른 카드 · 복습 기록 · 그림은 명령이 받지도 않는다.
- **받는 것**: `{"options": [보기, …]}` (strict `json_schema`).
- **지시문이 말하는 것** (`DISTRACTOR_INSTRUCTIONS`): 만들 수만큼, 정답과 뜻이 같거나 정답이 될 수 있는 보기는 쓰지 말 것(정답이 여럿이면 모두 정답), 이미 쓴 보기 · 앞 제안과 겹치지 말 것, 같은 문체 · 길이 · 언어, 번호나 설명을 붙이지 말 것. 예시는 없다.
- **코드가 확인하는 것** (`parse_distractors`): JSON 이 아니거나 `options` 가 없으면 전부 버린다. 그 밖에는 **보기 하나씩** 버린다: 빈 글, 80자를 넘는 글, 정답 · 보낸 보기 · 앞 제안 · 앞에서 받은 제안과 같은 글(띄어쓰기를 모두 빼고 대소문자 무시, `option_key`). 요청한 수까지만 남기고, 남는 것이 없으면 `BadOutput` ("알맞은 오답을 만들지 못했어요 · 다시 시도해 주세요", Q45).
- **화면이 하는 것**: 기다리는 동안 직접 쓴 보기와 같은 제안은 받을 때 버린다. 제안은 점선 줄로 뜨고 "AI가 지은 보기예요. 사실은 정답이 아닌지 확인한 뒤 넣어 주세요." 경고가 붙는다. [넣기] · [모두 넣기]를 누른 것만 첫 빈 보기 칸(없으면 끝)에 오답으로 들어간다. 저장은 평소의 추가 · 편집 길이고, 넣지 않은 제안은 버린 수만 알린다 (Q43).
- **코드가 확인하지 않는 것**:
  - 뜻이 정답과 같은 보기. "전송 계층"이 정답일 때 "4계층" · "Transport layer" · "L4", 한글 · 영문 · 약어 · 숫자 표기가 다른 같은 답은 모두 지난다.
  - 질문의 조건을 만족해 정답이 될 수 있는 다른 답. "다음 중 포유류는?"의 정답이 "고래"일 때 "박쥐"는 글자가 달라 지난다.
  - 번호 · 설명이 붙은 보기 ("1. ACK", "RST (연결 초기화)"). 지시문에만 있다.
  - 정답과 종류가 다른 엉뚱한 보기, 문체 · 길이 · 언어가 다른 보기.
  - 문장 부호만 다른 같은 보기 ("FIN-ACK" 와 "FIN ACK" 는 다른 보기로 본다). 반대로 대소문자만 다른 **다른** 보기는 같은 보기로 버린다 ("CO" 일산화탄소와 "Co" 코발트).
- **실패 기록**: 없다. `ai::log_failure` 를 부르지 않아 형식 오류가 `ai-errors.log` 에 남지 않는다.
- **측정**: 단위 테스트는 손으로 쓴 출력과 가짜 응답으로 `parse_distractors` 만 검사한다. 실제 ChatGPT 출력에서 정답이 될 수 있는 보기가 얼마나 섞이는지 잰 적이 없고, 평가셋이 없다.

정답인 보기가 오답으로 저장되면 학습자는 그 보기를 맞게 골라도 틀린 것으로 처리된다 (`recall_suggest` 가 Again 을 추천하고 "지난번" 표시에 남는다). 사용자가 넣기 전에 보지만, 표기만 다른 같은 답은 놓치기 쉽다.

### 1.2 목표

선택형 카드를 만드는 사용자에게, 정답이 아니면서 정답과 헷갈릴 만한 오답 보기를 필요한 수만큼 제안한다. 사용자는 고른 것만 넣는다.

### 1.3 맥락

- 대상: 선택형 카드를 쓰거나 고치는 사용자. ChatGPT 를 연결한 사람만 쓴다 (Q8 · Q40).
- 왜: 그럴듯한 오답을 손으로 3개씩 짓는 일이 카드 쓰기에서 가장 느리다.
- 위험: 정답이 오답 칸에 들어가면 카드가 학습자를 틀리게 가르친다. 다른 작업의 실수(채점 보조의 박한 판정, 초안의 어색한 문장)는 그 자리에서 보이고 사라지지만, 이 작업의 실수는 **카드에 저장돼 복습마다 되풀이된다.** 그래서 DS-SC-04 가 이 작업의 가장 중요한 지표다.
- 제안은 참고다. 넣을지는 사용자가 정한다 (Q8).

### 1.4 제약

**보기**

- 오답은 정답이 아니어야 한다. 정답과 뜻이 같은 다른 표기(약어 · 원어 · 번역 · 숫자 표기)도 정답이다. 질문의 조건을 만족하는 다른 답도 정답이다. 정답이 여럿이면 모두 정답이다 (Q41).
- 정답과 같은 종류여야 헷갈린다. 사람 이름이 정답이면 사람 이름, 계층이 정답이면 계층, 수가 정답이면 같은 단위의 수.
- 이미 쓴 보기와 같은 문체 · 길이 · 언어로, 보기 글자만 쓴다.

**코드가 맡는 것**

- 몇 개를 받을지는 화면이 정하고(Q37), 명령은 그 수까지만 보인다. 모델은 수를 정하지 않는다.
- 글자로 확인할 수 있는 것은 코드가 확인한다: 빈 글, 길이, 같은 글, 앞 번호 표시.
- **버리는 단위는 보기 하나다** (지금과 같음). 보기들은 서로 기대지 않고 사용자가 하나씩 보고 넣는다. 채점 보조가 전부 버리는 것은 판정이 기준 목록 전체를 덮어야 하기 때문인데, 여기에는 그런 구조가 없다. 하나가 걸렸다고 나머지를 버리면 사용자는 같은 요청을 다시 보내야 한다. JSON 이 깨졌거나 `options` 가 없으면 전부 버린다. (갈림길 1.8-③)
- 뜻이 정답과 같은지는 코드가 판단하지 않는다. 글자 비교로 거르면 "SYN-ACK" 이 정답일 때 "SYN" · "ACK" 처럼 좋은 오답을 버리고, 숫자 답("3" 과 "13")도 잘못 걸린다. 지시문과 경고 줄이 맡고 평가셋으로 잰다. (갈림길 1.8-② · ④)

**그대로 두는 것**

- 보내는 범위와 상한 (Q38 · Q42 · Q44), 첫 전송 확인 (Q39), 연결이 없으면 줄을 숨김 (Q40), 몇 개 (Q37), 오류 문구 (Q42 · Q45), 넣기 · 저장 · 버린 수 알림 (Q40 · Q43), 낮은 창 배치 (Q46).
- 화면의 경고 줄 "AI가 지은 보기예요. 사실은 정답이 아닌지 확인한 뒤 넣어 주세요."
- 같은 보기를 보는 기준(`option_key`: 띄어쓰기를 모두 빼고 대소문자 무시). "CO" 와 "Co" 처럼 대소문자만 다른 다른 보기를 버리는 일은 DS-SC-06 으로 잰다.

### 1.5 범위

포함: 지시문 · 스키마, 응답 검사(같은 글 · 길이 · 앞 번호), 수 자르기, 실패 기록, 평가셋과 측정 길.

제외:

- 정답과 뜻이 같은 보기를 코드로 거르는 것 (1.4)
- 오답마다 "왜 틀렸는지" 설명을 받는 것
- 정답 보기를 고치거나 질문을 고치는 제안
- 보기를 자동으로 넣는 것 (Q8)
- 형식 오류 뒤의 자동 재요청
- 한 창에서 쌓이는 피할 보기의 수 제한 (Q44 의 남은 문제 그대로)

### 1.6 출력 형식과 평가 지표

명령이 화면에 돌려주는 것 (지금과 같다):

```text
[보기, …]    1개 이상, 요청한 수 이하. 정답 · 보낸 보기 · 앞 제안 · 서로와 같은 글이 없다
             하나도 없으면 오류 bad_output
```

평가셋은 새로 만든다: `src-tauri/tests/fixtures/distractors-dev.jsonl`. 한 줄이 카드 하나다.

```text
id            항목 이름
case          유형 (아래)
question      질문 글자
correct       정답 [글, …]
wrong         이미 쓴 오답 [글, …] (비어도 된다)
also_correct  정답으로 쳐야 할 다른 글 [글, …]: 다른 표기, 질문의 조건을 만족하는 다른 답
```

유형: 다른 표기가 많은 답(약어 · 원어 · 번역) · 답이 여럿일 수 있는 질문("~인 것은?") · 정답 여럿(Q41) · 수 · 연도 · 이미 쓴 오답 없음 · 이미 쓴 오답 3개(1개 요청) · 영어 카드 · 대소문자만 다른 다른 보기가 있을 법한 답. 유형마다 3개 안팎, 모두 20–30개.

| 지표 | 잇는 기준 | 셈 |
|---|---|---|
| 정답 섞임 (목록) | DS-SC-04 | 보인 제안 가운데 `correct` · `also_correct` 와 같은 글(`option_key`)인 것. 코드가 센다. 목록에 없는 같은 답은 못 세므로 **하한**이다 |
| 정답 섞임 (사람) | DS-SC-04 | 보인 제안 가운데 사람이 읽고 "정답이 될 수 있다"로 표시한 것 |
| 엉뚱한 보기 | DS-SC-05 | 보인 제안 가운데 사람이 "정답과 종류 · 언어가 다르다"로 표시한 것 |
| 잘못 버린 비율 | DS-SC-06 | 코드가 버린 제안 가운데 사람이 "쓸 수 있는 다른 보기였다"로 표시한 것 |
| 결과 없음 비율 | DS-SC-03 | 호출 가운데 `bad_output` 으로 끝난 것 |
| 모자란 수 | — | 보인 제안이 요청한 수보다 적은 호출 |
| 정답 글자 포함 | — (참고) | 보인 제안 가운데 정답 글자(2자 이상)를 품은 것. 이것으로 거를지 정하려고 센다 |
| 모델이 낸 정답 | — (참고) | 모델이 낸 보기(검사 전) 가운데 `correct` · `also_correct` 와 같은 글인 것. 코드가 얼마나 막았는지 본다 |

기준 수치는 첫 측정 뒤 정한다. 정답 섞임은 잘못 받아들인 쪽, 잘못 버린 비율과 엉뚱한 보기는 지나치게 거른 쪽 · 쓸모없는 쪽이다. 한쪽만 줄이는 고침은 다른 쪽을 같이 본다.

### 1.8 정한 것과 아직 정하지 않은 것

2026-11-15 사용자가 네 갈림길을 모두 추천안으로 정했다.

| 갈림길 | 정한 것 | 다른 안 |
|---|---|---|
| ① 평가셋에서 "정답인 보기"의 판정 | 항목마다 `also_correct` 목록을 두어 코드가 자동으로 센다 (하한). 첫 측정은 사람이 보인 제안 · 버린 제안을 모두 읽어 표시하고, 읽다 찾은 같은 답은 목록에 더한다 | 목록만 (놓친 것을 모른다) · 사람만 (매번 전부 읽는다) |
| ② 임베딩 모델 | 앱에서는 쓰지 않는다. 측정 때 기기에 모델이 있으면 제안마다 정답과의 유사도를 결과에 같이 적고, 사람 표시와 견줘 쓸모를 본다 | 측정에도 쓰지 않음 · 앱에서 표시만 |
| ③ 버리는 단위 | 보기 하나씩 (1.4) | 하나라도 걸리면 전부 버림 |
| ④ 정답 확인 호출 | 지금은 두지 않는다 | 받은 보기마다 "질문의 답이 될 수 있는가"를 다른 호출로 묻는다 (요청 수와 기다림이 두 배) |

아직 정하지 않은 것:

- 지표의 기준 수치 → 첫 측정 뒤 (6.4)
- 정답 확인 호출 · 유사도 표시 · 정답 글자 포함 검사를 더할지 → 첫 측정의 정답 섞임 · 유사도 · 정답 글자 포함 값을 보고

## 2. Skill

모델에게 맡기는 일은 하나다: 질문과 정답을 보고 정답이 아닌 그럴듯한 보기를 짓는다. 몇 개를 받을지, 같은 보기인지, 형식이 맞는지는 코드가 맡는다.

| | 오답 짓기 |
|---|---|
| 하는 일 | 정답과 같은 종류이지만 정답이 아닌 보기를 "만들 오답 수"만큼 짓는다 |
| 언제 | [오답 보기 N개 제안 받기] · [다시 제안] · [다시 시도]를 누를 때 |
| 받는 것 | 질문, 정답(여럿일 수 있다), 이미 쓴 오답, 앞서 받은 제안, 만들 오답 수 |
| 내는 것 | `{"options": [보기, …]}` |
| 하지 않는 것 | 정답 고르기 · 고치기, 보기마다 설명, 수 정하기 |

### 2.1 지시문

```text
선택형 암기 카드의 오답 보기를 만드는 일을 도와요. 사용자가 질문, 정답, 이미 쓴 오답, 만들 오답 수를 보내요.
- "만들 오답 수"만큼 새 오답 보기를 만드세요.
- 정답이 될 수 있는 보기는 쓰지 마세요. 정답이 여러 개면 모두 정답이에요. 이런 것도 정답이에요:
  - 정답을 다르게 적은 것: 약어, 원어, 번역, 다른 숫자 표기 (이산화탄소 = CO₂ = carbon dioxide)
  - 질문의 조건을 만족하는 다른 답 (포유류를 묻고 정답이 고래면 박쥐도 정답이에요)
- 정답과 같은 종류로 쓰세요. 계층이 정답이면 계층, 사람이 정답이면 사람, 수가 정답이면 같은 단위의 수. 헷갈릴 만하지만 분명히 틀린 보기여야 해요.
- 이미 쓴 보기와 같은 문체 · 길이로, 질문과 같은 언어로 쓰세요. 이미 쓴 오답 · 앞서 제안한 오답과 겹치지 마세요.
- 보기 글자만 쓰세요. 번호나 설명은 붙이지 마세요.
- 답은 {"options": [보기, …]} 모양의 JSON 하나만.

예시
질문: OSI 7계층에서 TCP가 속한 계층은?
정답: 전송 계층
이미 쓴 오답:
- 네트워크 계층
만들 오답 수: 2
→ {"options": ["세션 계층", "데이터 링크 계층"]}
```

지금 지시문과 다른 점: 정답이 될 수 있는 것을 두 종류로 풀어 적었고(다른 표기, 조건을 만족하는 다른 답), 같은 종류로 쓰라는 줄과 예시를 더했다. 예시의 출력은 "4계층" · "Transport layer" 를 쓰지 않는다.

지시문 안의 보기(이산화탄소 · 포유류 · OSI 계층)는 평가셋에 넣지 않는다. 넣으면 모델이 예시를 따라 해 측정이 흐려진다 (`distractor_eval_set_is_well_formed` 가 막는다).

### 2.2 출력 스키마

지금과 같다.

```json
{ "type": "object", "additionalProperties": false, "required": ["options"],
  "properties": { "options": { "type": "array", "items": { "type": "string" } } } }
```

개수(`maxItems`)는 스키마에 두지 않는다. strict 스키마가 받지 않을 수 있고, 코드가 자른다 (DS-H-09).

### 2.3 품질 점검

| 조건 | 지금 | 이 Skill |
|---|---|---|
| 단일 기능 | 통과. 보기만 낸다 | 통과 |
| 명확한 설명 | 통과. 첫 줄이 무엇을 받아 무엇을 하는지 말한다 | 통과 |
| 범위 명시 | 부분. "정답이 될 수 있는 보기"가 무엇인지 말하지 않는다 | 통과. 두 종류를 예와 함께 적었다 |
| 예시 포함 | **실패. 예시가 없다** | 통과. 입출력 한 쌍 |
| 확인 가능 | 아래 표 | 아래 표 |

### 2.4 지시문의 규칙을 무엇으로 확인하는가

| 규칙 | 확인 |
|---|---|
| 만들 수만큼 | 코드: 넘으면 자른다 (DS-H-09). 모자라면 그대로 보이고 평가셋의 "모자란 수"로 센다 |
| 정답과 같은 글을 쓰지 않는다 | 코드 (DS-H-08) |
| 정답의 다른 표기 · 조건을 만족하는 다른 답을 쓰지 않는다 | 평가셋 (정답 섞임) |
| 같은 종류 · 같은 문체 · 같은 언어 | 평가셋 (엉뚱한 보기) |
| 이미 쓴 보기 · 앞 제안과 겹치지 않는다 | 코드 (DS-H-08) |
| 번호를 붙이지 않는다 | 코드: 뗀다 (DS-H-06) |
| 설명을 붙이지 않는다 | 코드는 80자 상한만 (DS-H-07). 짧은 설명은 평가셋 (엉뚱한 보기) |
| JSON 하나만 | 코드 (DS-H-05) |

## 3. Subagent

호출은 한 번이다. 그 경계를 적는다.

### 3.1 경계

| 경계 | 오답 짓기 호출 |
|---|---|
| 입력 형식 | 질문 글자, 정답, 이미 쓴 오답, 앞서 받은 제안, 만들 오답 수 (3.2) |
| 출력 형식 | 2.2 의 스키마 |
| 도구 권한 | 없음 |
| 독립 컨텍스트 | 새 대화. [다시 제안]도 앞 대화를 잇지 않고 앞 제안 글만 받는다 |

### 3.2 입력 형식

지금과 같다 (`distractor_input`).

```text
질문: <질문 글자>
정답: <정답>                          (여럿이면 줄마다)
이미 쓴 오답:                          (없으면 이 머리도 없다)
- <보기>
앞서 제안한 오답 (다시 쓰지 마세요):   (없으면 이 머리도 없다)
- <보기>
만들 오답 수: <N>
```

- 질문은 편집기 HTML 에서 태그 · 그림 · 소리 표시를 뺀 화면 글자, 600자. 보기는 칸 글자에서 소리 표시를 빼고 띄어쓰기를 하나로, 200자. 넘으면 잘라 "…(잘림)"을 붙인다 (`rag::clip`).
- 이미 쓴 오답은 사용자가 확인 목록에서 ✕ 로 뺀 것을 빼고 보낸다 (Q38). 앞서 받은 제안도 ✕ 로 빼면 보내지 않는다 (Q44).
- N 은 화면이 센 수이고(Q37), 명령이 5 를 넘지 않게 자른다.

### 3.3 출력 형식

- 2.2 의 스키마를 `json_schema`(strict)로 요청한다. 형식 지정을 받지 않는 모델이면 형식 없이 다시 보내고 (I76), 어느 쪽이든 받은 글은 5절의 검사를 지난다.
- 이 작업은 모델이 새 글을 짓는 일이라 번호로 가리키게 할 수 없다 (채점 보조의 원칙 "모델은 번호로만 가리킨다"가 맞지 않는다). 대신 화면에 보이는 글은 코드가 다듬은 글이다: 소리 표시를 빼고, 띄어쓰기를 하나로, 앞 번호 표시를 뗀 것 (DS-H-06).

### 3.4 도구 권한

- 모델에게 도구를 주지 않는다. 요청은 `store: false` 다.
- 모델은 카드를 바꿀 수 없다. 명령은 DB 를 받지 않고(`AppState` 가 없다) 글자만 받아 글자만 돌려준다. 보기 칸에 넣는 것은 사용자의 [넣기]이고, 저장은 평소의 카드 추가 · 편집 명령이다.

### 3.5 독립 컨텍스트

- 앞 대화 없이 지시문과 입력 하나로 시작한다.
- 보내지 않는 것은 Q38 그대로다: 덱 이름, 다른 카드, 복습 기록, 그림, 자료 구간, 추가 설명 필드, 정답이 몇 번 칸인지.

## 4. Workflow

### 4.1 흐름

```text
[편집기에서 선택형 카드를 쓴다]
  줄 상태 (화면 · 아무것도 보내지 않는다)
       연결 없음 ──────────────→ 줄을 숨김 (Q40)
       정답 체크 없음 ─────────→ 줄을 끔 "정답에 체크하면 받을 수 있어요"
       보기 6개 ──────────────→ "보기가 6개라 더 받을 수 없어요"
       그 밖 ─────────────────→ [오답 보기 N개 제안 받기] · 보내는 범위 한 줄

[오답 보기 N개 제안 받기]
  이 기기에서 처음이면 확인 목록 (Q39). ✕ 로 보기 · 앞 제안을 뺄 수 있다
  ① 입력 확인 (코드)
       질문이 비었다 · 정답이 없다 · 받을 수가 0 ──→ 오류 한 줄
  ② 오답 짓기 호출 ──→ 보내지 못함 ──────────────→ 오류 한 줄 (Q42)
  ③ 검사 (코드)
       JSON 이 아니다 · options 가 없다 ────────────→ 결과 없음 (형식 오류) · 기록
       보기마다: 다듬기 → 앞 번호 떼기 → 빈 글 · 긴 글 · 같은 글이면 그 보기만 버림
       요청한 수까지 남긴다
       남은 것이 없다 ─────────────────────────────→ 결과 없음 (형식 오류) · 기록
  ④ 화면이 받을 때: 그사이 직접 쓴 보기와 같은 제안은 버림
       다 버려졌다 ────────────────────────────────→ 결과 없음 (형식 오류)
  ⑤ 제안 줄 (점선) + 경고 "사실은 정답이 아닌지 확인한 뒤 넣어 주세요"
       [넣기] · [모두 넣기] ──→ 첫 빈 보기 칸 (없으면 끝, 6개에서 멈춤)
       [빼기] ──→ 그 제안만 지움 (다음 [다시 제안]에서 피할 보기로)
       [다시 제안] ──→ ①로. 앞 제안을 피할 보기로 보낸다

[저장]  평소의 카드 추가 · 편집. 넣은 보기만 저장된다. 남은 제안은 버린 수만 알린다 (Q43)
```

### 4.2 단계 사이에 넘기는 것

| 단계 | 받는 것 | 넘기는 것 |
|---|---|---|
| ① 입력 확인 | 질문 HTML, 정답 글, 보낼 오답 글, 앞 제안 글, 수 | 다듬은 글들, 자른 수 |
| ② 호출 | ①의 것 | 모델이 낸 글 |
| ③ 검사 | 모델이 낸 글, 정답 · 보낸 오답 · 앞 제안 (같은 글 비교용), 수 | 보일 제안 (또는 형식 오류와 버린 까닭별 수) |
| ④ 받기 | 보일 제안, 지금의 편집기 보기 | 새 제안 |
| ⑤ 넣기 | 고른 제안 | 편집기 보기 칸 (저장 전) |

①–③은 한 명령(`ai_distractors`) 안에서 돈다. ④⑤는 화면(`DistractorLine`)이다.

### 4.3 종료 상태

| 상태 | 언제 | 화면 |
|---|---|---|
| 제안 받음 | 검사와 받기를 지나 하나 이상 남았다 | 점선 제안 줄과 경고 줄, "보낸 것 · …" |
| 결과 없음 (형식 오류) | ③ 또는 ④에서 하나도 남지 않았다 | "알맞은 오답을 만들지 못했어요 · 다시 시도해 주세요" [다시 시도] (Q45). ③에서 끝났으면 `ai-errors.log` 에 한 줄 |
| 결과 없음 (보내지 못함) | 만료 · 권한 · 한도 · 오프라인 · 잠시 못 씀 · 요금제 안 됨 | 지금의 오류 문구 그대로 (Q42) |
| 멈춤 | [취소] · 카드 추가에서 저장 · 창을 닫음 | 요청을 멈추고 "멈췄어요" 토스트. 제안은 없다 |
| 보내지 않음 | 질문이 비었다 · 정답이 없다 · 보기 6개 | 줄의 안내 그대로 |

어느 상태에서도 보기를 직접 쓰고 저장할 수 있다. 기다리는 동안에도 그렇다 (Q42).

### 4.4 다시 하기와 횟수

- 형식 오류 뒤에 자동으로 다시 보내지 않는다. 사용자가 [다시 시도]를 누른다.
- 연결 층의 다시 하기는 그대로다: 401 이면 토큰을 한 번 새로 받아 다시, 형식 지정을 받지 않으면 형식 없이 한 번 다시 (I76 · I77).
- "이번 달 보낸 수"는 요청마다 하나씩 오른다.
- 보기 하나가 검사에 걸려 수가 모자라도 다시 보내지 않는다. 모자란 채 보인다.

## 5. Hook

모델의 판단과 상관없이 코드가 **항상** 돌리는 검사다. 걸렸을 때 하는 일은 넷 중 하나다.

- **오류**: 보내지 않고 오류 한 줄.
- **전부 버림**: `AiError::BadOutput` 을 내고 제안을 하나도 보이지 않는다.
- **그 보기만 버림**: 나머지는 그대로 보인다 (1.4, 갈림길 ③).
- **고침**: 값을 다듬거나 자르고 계속한다.

### 5.1 보내기 전

| ID | 검사 | 걸리면 | 코드 |
|---|---|---|---|
| DS-H-01 | 질문이 태그 · 소리 표시를 빼고도 비지 않았는가 | 오류 "질문을 먼저 써 주세요." | `ai_distractors` |
| DS-H-02 | 정답이 하나 이상인가 | 오류 "정답에 체크한 뒤 받을 수 있어요." (화면은 줄을 먼저 끈다) | `ai_distractors` |
| DS-H-03 | 받을 수가 1–5 인가. 5 를 넘으면 5 로 | 0 이면 오류 "보기가 6개라 더 받을 수 없어요." | `ai_distractors` |
| DS-H-04 | 보내는 글이 상한 안인가 (질문 600자, 보기 200자) | 고침 (자르고 "…(잘림)") | `distractor_input` |

### 5.2 응답을 받을 때

| ID | 검사 | 걸리면 | 코드 |
|---|---|---|---|
| DS-H-05 | JSON 이고 `options` 가 배열인가 | 전부 버림 | `parse_distractors` |
| DS-H-06 | 보기를 칸 글자처럼 다듬는다 (소리 표시 빼기, 띄어쓰기 하나로). 앞 번호 표시(`quality::item_marker`: ① · 1. · 1) · (1) · - · • · ·)가 있고 **그 뒤에 띄어쓰기가 오면** 뗀다 | 고침. "1. ACK" → "ACK". "1.5배" · "-273℃" · "①번" 은 그대로 | `distractor_text` |
| DS-H-07 | 다듬은 보기가 비지 않았고 80자 이하인가 (글자가 아닌 값은 빈 글로 본다) | 그 보기만 버림 | `sort_distractors` |

### 6.3 평가를 돌리는 방법

채점 보조(grade.md 6.3)와 같은 방식이다. 실제 ChatGPT 출력은 **앱 안에서 로그인한 계정으로** 잰다.

- debug 빌드에서만 듣는 환경 변수로 시작한다: `ADDIEM_DISTRACTOR_EVAL=<결과 파일>` 을 주고 앱을 띄우면 돈다. `ADDIEM_DISTRACTOR_EVAL_SET=<jsonl>` (없으면 `src-tauri/tests/fixtures/distractors-dev.jsonl`), `ADDIEM_DISTRACTOR_EVAL_LIMIT=n` (앞 n개). 릴리스 빌드는 듣지 않는다. 시작은 `lib.rs` 의 한 줄(`recall::eval_on_start`)이다.
- 평가셋은 24개다. 유형 8개 × 3: `notation`(다른 표기) · `open`(답이 여럿일 수 있는 질문) · `multi`(정답 여럿) · `number`(수 · 연도) · `empty`(이미 쓴 오답 없음, 3개 요청) · `full`(이미 쓴 오답 3개, 1개 요청) · `english` · `case`(대소문자만 다른 다른 보기가 있을 법한 답: CO · N · MB).
- 받을 수는 화면과 같은 규칙(Q37)으로 정답 수 + 오답 수에서 센다.
- 항목마다 앱과 같은 차례로 두 번 부른다:
  1. `1`: 정답 · 오답을 보낸다.
  2. `again`: 1 에서 보인 제안을 앞 제안으로 보낸다 ([다시 제안]).
- 결과는 한 줄에 호출 한 번씩 JSON 으로 남긴다: 실행 시각, 모델 이름, 지시문 해시, 항목 id · 유형, 몇 번째, 요청한 수, 모델이 낸 보기(검사 전), 보인 제안, 버린 보기와 까닭, 오류. 기기에 임베딩 모델이 있으면 보인 제안마다 정답과의 유사도(정답이 여럿이면 가장 큰 값)를 더한다. **시각 · 모델 · 해시는 코드가 적는다.**
- 자동 지표는 결과 줄에서 코드가 세어 `<결과 파일>.summary.txt` 와 stderr 에 쓴다 (`distractor_eval_summary`).
- 사람이 읽을 표를 `<결과 파일>.review.tsv` 로 쓴다. 한 줄에 보기 하나: 항목 id, 몇 번째, 질문, 정답, 보임 / 버림(까닭), 보기, 목록 일치, 유사도, **표시(빈칸)**. 사람이 표시 칸을 채운다.
  - 보인 보기: `ok`(쓸 만한 오답) · `정답`(정답이 될 수 있다) · `엉뚱`(종류 · 언어 · 형식이 다르거나 설명이 붙었다)
  - 버린 보기: `ok`(버릴 만했다) · `다른 보기`(실제로는 다른 보기였다. 예: "CO" 와 "Co")
  - 넘침으로 버린 보기는 표시하지 않는다 (수를 맞춘 것이지 걸러 낸 것이 아니다).
- 사용량: 요청 48회 안팎이고 "이번 달 보낸 수"에 들어간다. 한도 · 오프라인 · 로그인 문제면 거기서 멈추고 그때까지의 결과를 남긴다.
- 읽다 찾은 같은 답은 그 항목의 `also_correct` 에 더한다. 다음 측정부터 자동 셈에 들어간다.

정답 섞임은 잘못 받아들인 쪽이고, 잘못 버린 비율과 엉뚱한 보기는 지나치게 거르거나 쓸모없는 쪽이다. 고친 뒤에는 양쪽을 같이 본다. 기준 수치는 첫 측정값을 보고 사용자가 정한다.

유사도는 기준 수치를 두지 않는다. 첫 측정에서 `정답` 표시와 `ok` 표시의 유사도가 갈리는지 보고, 앱에 쓸지(갈림길 ②)를 다시 정한다.

### 6.5 사람이 확인하는 것

화면 (debug 빌드, `ADDIEM_AI_FAKE=ok` · `malformed` · `slow`). 모두 미실행.

- [ ] 제안 받음: 선택형 카드 추가(C3)에서 질문 · 정답 1개 · 오답 1개를 쓰고 받으면 제안 2개가 점선으로 보이고 경고 줄이 붙는다. 가짜 응답의 "1. ACK" 는 "ACK" 로 보인다
- [ ] [넣기] 한 것만 보기 칸에 들어가고, 넣지 않고 저장하면 "넣지 않은 제안 N개는 버렸어요"가 보인다. 저장한 카드에 넣지 않은 제안이 없다 (DS-SC-08)
- [ ] [다시 제안]은 앞 제안과 다른 보기를 준다. 가짜 목록을 다 쓰면 "알맞은 오답을 만들지 못했어요 · 다시 시도해 주세요"와 [다시 시도]가 보이고 `ai-errors.log` 에 `ai_distractors` 한 줄이 남는다 (보기 글자 없이)
- [ ] `malformed`: 형식 오류 줄과 기록 한 줄
- [ ] 카드 편집(E)에서도 같다. 기다리는 동안 창을 닫으면 요청이 멈춘다
- [ ] 실제 연결에서 한 번

### 6.6 이 평가셋이 재지 못하는 것

| 재지 못하는 것 | 까닭 | 지금의 확인 |
|---|---|---|
| 긴 질문 · 문장형 보기 | 항목이 모두 짧은 낱말 답이다 | 자르기는 단위 테스트 |
| 그림 · 소리가 있는 질문 | 평가셋은 글자만이다 | 빼고 보내는 것은 단위 테스트 |
| 여러 번 [다시 제안]해 피할 보기가 쌓인 경우 | 두 번만 부른다 | 재지 않는다 |
| 사용자가 ✕ 로 오답을 뺀 경우 | 보낸 오답을 그대로 쓴다 | 재지 않는다 |

채워야 할 때 항목을 더한다. 지금은 더하지 않는다.

평가셋의 사실(정답 · `also_correct`)은 코드를 쓴 쪽이 일반 교과 지식으로 적었고 원 출처와 대조하지 않았다. 사용자가 읽고 확인한다 (미실행).
