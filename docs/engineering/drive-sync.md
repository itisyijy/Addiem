# Google Drive 보관·동기화 설계

## 문서 상태

- 버전: v0.1
- 상태: **구현 중.** MVP 범위 8.6(Later)이지만 작성자가 G·H·I·J와 함께 지금 진행하기로 정했다 (2026-10-14). 6장 스키마 선행 작업은 들어갔다
- 화면: Figma Row K (K0 흐름 보드, K1–K10). [Neo-Anki MVP UI](https://www.figma.com/design/xZsmRhJ4rvkjwYHfQyM5jx)
- 관련: [ADR 0001](../adr/0001-tech-stack.md) "서버는 MVP 범위에 없다", [데이터 모델](data-model.md), [검토 대기 목록](../DECISIONS-PENDING-REVIEW.md) K절

## 1. 왜 Drive인가

인터뷰 진술 두 개가 근거다 ([파워 유저 인터뷰](../user-research/anki-power-user-interview.md) "동기화와 파일 관리").

- AnkiWeb이 앱을 닫을 때 진행 상황을 자동으로 맞춰 주는 점을 매우 좋게 봤다.
- AnkiWeb 말고 개인 드라이브 같은 다른 클라우드 선택지가 있으면 좋겠다고 했다.

Drive를 저장소로 쓰면 **Neo-Anki 서버가 필요 없다.** 계정 시스템, 서버 운영비, 서버가 사용자 데이터를 보관하는 문제가 모두 사라진다. local-first 원칙과 맞는다. 대가는 서버가 없으니 합치는 일을 각 기기가 해야 한다는 점이다 (5장).

## 2. 원칙

| 원칙 | 형태 |
|---|---|
| 연결은 선택이다 | 기본으로 꺼져 있다. 연결 전에는 앱이 네트워크를 쓰지 않는다 |
| 이 기기가 정본이다 | 로컬 DB가 항상 먼저 쓰이고, Drive는 뒤따른다. 언제 꺼도 잃는 것이 없다 |
| 복습 기록은 잃지 않는다 | 합칠 때 지우거나 덮어쓰지 않는다 |
| 같은 파일을 두 기기가 고치지 않는다 | 기기마다 자기 파일만 새로 쓴다. 여럿이 고치는 공유 파일이 없다 |
| 다른 기기 데이터를 몰래 덮지 않는다 | 덮어쓰는 결정(되돌리기, 새로 시작)은 다른 기기에서도 고르는 창(K6-m)을 거친다 |
| 학습을 방해하지 않는다 | 학습 중에는 동기화하지 않고, 알림도 학습이 끝난 뒤에 보여준다 |

## 3. 연결 (K1–K3)

| 항목 | 결정 |
|---|---|
| 로그인 | 시스템 기본 브라우저로 OAuth 2.0. PKCE + `127.0.0.1` 루프백 리다이렉트. 앱 안 웹뷰 로그인은 쓰지 않는다 (Google 정책상 막혀 있다) |
| 권한 | `drive.file`(앱이 만든 파일만) + `drive.appdata`(앱 전용 숨김 공간). 둘 다 Google 분류상 민감하지 않은 범위다. Drive 전체 권한은 요청하지 않는다 |
| 토큰 보관 | OS 키체인(Windows 자격 증명 관리자, macOS 키체인). DB나 파일에 쓰지 않는다 |
| 네트워크 위치 | 웹뷰는 네트워크를 쓰지 않는다. Drive 호출은 앱 백엔드(Rust)가 한다. 웹뷰 CSP `connect-src` 는 연결한 뒤에도 열지 않는다 (I16 그대로) |
| OAuth 클라이언트 | Google Cloud에 등록한 데스크톱 앱 클라이언트 ID를 빌드할 때 넣는다. 없는 빌드는 K1-n: [Google Drive 연결] 비활성 + "이 빌드에는 Google 연결이 설정되지 않았어요". 빈 홈(K6)의 불러오기 줄도 숨긴다 |
| Google 앱 인증 | 인증 전에는 "확인되지 않은 앱" 경고가 뜨고 테스트 사용자는 100명까지다. 출시 전에 브랜드 인증을 받는다 |

사용자가 동의 화면에서 권한 하나를 빼면 "권한 2개가 모두 필요해요"를 보여주고 다시 연결하게 한다.

## 4. Drive 안의 구조

```text
내 드라이브/Neo-Anki 백업/              ← drive.file, 사용자에게 보인다
  neoanki-2026-10-14-0912.zip          카드·기록·설정만 (약 6MB)

appDataFolder/                          ← drive.appdata, Drive 화면에 안 보인다
  devices/<device_uid>.json             기기 이름, 마지막 동기화, 기기별로 어디까지 받았는지
  snapshot/g<세대>-<device_uid>-<seq>.db.gz   전체 상태 압축본
  changes/<device_uid>/<seq>.jsonl.gz   그 기기의 변경 묶음. 새 파일로만 쓴다
  media/<sha256>.<ext>                  그림. 내용 해시가 이름이라 같은 파일은 한 번만
  crypto.json                           (암호 잠금을 켰을 때만) salt, KDF 매개변수, 키 확인값
```

- **공유되는 가변 파일이 없다.** `devices/` 는 기기마다 자기 파일만 고치고, `snapshot/`·`changes/`·`media/` 는 새로 만들기만 한다. Drive API v3에는 조건부 쓰기가 없으므로, 동시 쓰기 충돌을 구조로 없앴다.
- 세대 번호는 가장 높은 `snapshot/g<세대>` 에서 읽는다. 되돌리기(K9)나 "이 기기 데이터로 새로 시작"(K6-m)은 세대를 하나 올린 스냅샷을 쓴다.
- Drive 백업 zip에는 그림을 넣지 않는다. 그림은 `media/` 에 한 번만 두고, 남아 있는 백업이 참조하는 그림은 지우지 않는다. 그림까지 든 zip이 필요하면 앱에서 [그림까지 묶어 내려받기]로 만든다. 그림을 매번 넣으면 백업 12개가 약 4GB를 차지한다.

## 5. 동기화

### 5.1 언제

| 시점 | 하는 일 |
|---|---|
| 앱 실행 | 받기 → 올리기 |
| 학습을 마칠 때 (D5, 그만하기) | 올리기 |
| 창을 닫을 때 | 올리기. 최대 10초 기다리고 닫는다 (K8) |
| 앱이 열려 있을 때 | 30분마다 받기. 학습 중에는 하지 않는다 |
| [지금 동기화] | 받기 → 올리기. 학습 중에는 누를 수 없다 |

학습 중에 올리지 않으므로 되돌리기(I22, 방금 쓴 복습 기록 한 줄 삭제)는 항상 아직 올리지 않은 기록에만 일어난다.

### 5.2 올리기

1. `sync_outbox` 에서 마지막으로 올린 번호 뒤의 변경을 모은다 (6장).
2. 행 단위 변경을 `changes/<내 기기>/<seq>.jsonl.gz` 새 파일 하나로 쓴다. 참조는 정수 id가 아니라 `uid` 로 한다.
3. 새 그림은 `media/<sha256>` 이 없을 때만 올린다.
4. 그날 첫 올리기라면 Drive 백업 zip을 만들고 보관 규칙을 적용한다: 최근 7일은 하루 하나, 그 전은 주 하나, 최대 12개.
5. `devices/<내 기기>.json` 을 갱신한다.

### 5.3 받기

1. 다른 기기의 `changes/` 에서 아직 적용하지 않은 파일을 내려받는다.
2. 받은 변경을 아래 규칙으로 한 트랜잭션 안에서 적용한다. 적용하는 동안에는 `sync_outbox` 에 쌓지 않는다.
3. 실패하면 트랜잭션을 되돌리고 다음에 다시 시도한다. 받다 만 상태는 남지 않는다.

### 5.4 합치는 규칙

| 대상 | 규칙 |
|---|---|
| 복습 기록 `review_log` | 합집합. `uid` 가 같으면 같은 기록이다. 지우지 않는다 |
| 복습 일정 (FSRS 상태) | 마지막 공통 시점 뒤에 두 기기 이상에서 복습된 카드는 합친 기록을 시간 순으로 FSRS에 다시 돌려 계산한다. 한 기기에서만 복습됐으면 그 기기의 상태를 그대로 쓴다 |
| 카드·노트 내용 | **v1: 나중에 동기화한 쪽이 이긴다** (벽시계상 나중에 고친 쪽이 아니다). 진 쪽 내용은 30일 동안 따로 기록하고(G2 변경 기록과 별개), K4 "두 기기에서 고친 카드"와 K7에서 고를 수 있다. 화면 문구는 "나중에 동기화한 쪽으로 맞췄어요" |
| 덱 구조·설정·중요도 | 열 단위로 나중 것. 덱 이동(`parent_id`)과 이름은 따로 센다 |
| 삭제 | 지운 시각이 그 행을 마지막으로 고친 시각보다 나중일 때만 지운다. 고친 쪽이 나중이면 되살린다 |
| 그림 | `sha256` 이 같으면 같은 파일이다 |
| 세션·하루 계획 | 기기별로 따로 둔다. 같은 날 두 기기에서 공부하면 합계로 본다 |
| 처음 합칠 때 (K6-m "둘 다 남기고 합치기") | 따로 쓰던 두 데이터는 `uid` 가 모두 다르다. 같은 .apkg에서 온 노트만 `anki_guid` 로 같은 노트로 보고 하나로 합친다. 이름 경로가 같은 덱은 같은 덱으로 본다 |

**v1은 시각을 비교하지 않는다.** 동기화 순서로 정하므로 시계가 틀린 기기 문제는 없지만, 오래 오프라인이던 기기가 늦게 맞추면 그 기기의 오래된 수정이 이긴다. 30일 기록과 K7 토스트로 되돌릴 수 있게 한 이유다. ponytail: 이런 일이 실제로 잦으면 각 변경에 HLC `(물리 시각, 카운터, device_uid)` 를 붙여 "나중에 고친 쪽"으로 바꾸고 문구도 함께 바꾼다.

### 5.5 정리 (스냅샷)

- 변경 파일이 200개를 넘거나 마지막 스냅샷이 30일 지났으면, 받기를 마친 기기가 새 스냅샷을 쓴다. 두 기기가 동시에 써도 둘 다 올바른 스냅샷이고, 더 많이 포함한 쪽을 쓴다.
- 오래된 변경 파일은 그것을 포함한 스냅샷이 있고 **활성 기기가 모두 받았을 때만** 지운다 (`devices/*.json` 의 받은 위치로 판단).
- 90일 동안 동기화하지 않은 기기는 "오래 안 씀"으로 보고 기다리지 않는다. 그 기기를 다시 켜면 스냅샷부터 받고, 자기 로컬 변경을 5.4 규칙으로 합쳐 올린다.

## 6. 스키마 선행 작업

정수 PK만으로는 동기화할 수 없어 아래를 먼저 넣었다 (2026-10-14, 구현 세션). 변경·삭제 기록은 동기화를 켰을 때만 쌓이고, 받은 변경을 적용하는 동안에는 쌓지 않는다 (되받은 변경을 다시 올리지 않게).

| 문제 | 바꿀 것 |
|---|---|
| 모든 테이블이 `INTEGER PRIMARY KEY` 다. 두 기기에서 만든 id가 겹친다 | 동기화 대상 테이블에 `uid TEXT` + 유일 인덱스 `idx_{t}_uid` (INSERT 트리거가 채운다. 시간 순으로 정렬되는 32자 id: 앞 12자리 ms 시각 16진수 + 뒤 20자리 난수). 정수 id는 기기 안에서만 쓴다 |
| 삭제가 `DELETE` + `ON DELETE CASCADE` 라 지운 사실이 남지 않는다 | `sync_tombstone(table_name, uid, deleted_at)` (ms 시각). 삭제 트리거로 쌓는다. 지운 HLC는 올릴 때 매겨 `sync_row.deleted` 에 둔다 |
| 무엇이 바뀌었는지 모은 곳이 없다 | `sync_outbox(seq, table_name, uid, op, at, cols)`. INSERT/UPDATE/DELETE 트리거로 쌓는다. `at` 은 ms 시각, `cols` 는 바뀐 열 목록(UPDATE). HLC는 올릴 때 `at` 순서로 매긴다 |
| 기기 구분이 없다 | `schema_meta` 에 `device_uid`, `device_name`, `hlc_last`. 켜고 끄기는 `sync_flags(enabled, applying)`, 행·열 HLC는 `sync_row(table_name, uid, hlc, cols, deleted)` |
| `card_template` 에 `updated_at` 이 없다 | 열을 더한다 (`review_log` 는 바뀌지 않으므로 필요 없다) |

동기화 대상(`db::SYNC_TABLES`): `deck`, `deck_config`, `note_type`, `card_template`, `note`, `card`, `review_log`, `media`, `study_session`, `daily_plan`, `plan_setting`, `plan_shift`, `plan_conflict`, `source_material`, `source_segment`, `source_link`, `note_written`, `written_answer`. 대상이 아닌 것: `session_card_state`(세션 안에서만 의미), `import_batch`·`import_issue`(그 기기의 가져오기 보고), `schema_meta` 의 기기별 값(하루 시작 시각 포함).

마이그레이션은 [데이터 모델 9장](data-model.md) 규칙대로 적용 전에 자동 백업한다.

## 7. 암호로 잠그기 (선택, 기본 꺼짐)

- 비밀번호로 Argon2id 키를 만들고, 파일마다 XChaCha20-Poly1305로 암호화해 올린다. 비밀번호와 키는 Drive에 올리지 않고 OS 키체인에만 둔다.
- 잠그면 그림 파일 이름을 평문 해시 대신 키를 넣은 HMAC으로 바꾼다. 평문 해시는 "같은 그림이 있다"는 사실을 드러낸다.
- 비밀번호를 잊으면 Drive 쪽 데이터는 복구할 수 없다. 이 기기 데이터는 그대로다. 켤 때 이 사실을 한 번 더 확인받는다.

## 8. 실패와 표시 (K5)

| 상황 | 동작 | 상단 바 |
|---|---|---|
| 오프라인 | 변경을 로컬에 쌓아 둔다. 연결되면 저절로 올린다 | 회색 아이콘 + 대기 묶음 수 |
| 토큰 만료 / 권한 취소 | 동기화를 멈춘다 | 노란 "다시 로그인" |
| Drive 공간 부족 | 백업부터 멈추고, 변경은 로컬에 쌓아 둔다 | 노란 "Drive 공간 부족" |
| Drive 데이터의 스키마가 앱보다 새 버전 | 받지 않는다 | "앱을 업데이트해 주세요" |
| 사용자가 Drive에서 백업 폴더를 지움 | 다음 백업 때 새로 만든다. 동기화 데이터는 숨김 공간이라 영향이 없다 | 표시 없음 |
| Drive API 속도 제한 | 지수 백오프로 다시 시도한다 | 진행 고리 유지 |

빨간색은 쓰지 않는다. 어떤 경우에도 데이터는 이 기기에 남아 있다.

## 9. 남은 질문

| 질문 | 영향 |
|---|---|
| 원자료 파일(8.4)을 동기화할 때 큰 파일을 어떻게 올릴 것인가 | 재개 가능한 업로드(resumable upload)가 필요하다. 기본은 꺼짐이라 뒤로 미뤘다 |
| 모바일 복습 클라이언트(ADR 0001)가 같은 구조를 쓸 수 있는가 | 웹·모바일에서 `drive.appdata` 접근은 가능하다. FSRS 재계산을 클라이언트마다 같은 결과로 만들어야 한다 |
| GitHub 같은 다른 저장소 | 4장 구조는 "파일을 새로 쓰고, 목록을 보고, 내려받기"만 쓴다. 같은 인터페이스로 다른 저장소를 붙일 수 있다 |
