# 스파이크 1. Anki 패키지 구조 실측

## 문서 상태

- 실행일: 2026-09-20
- 대상: 작성자 본인의 컬렉션 내보내기 `itisyijy.colpkg` (13MB, 노트 4,694장)
- 목적: [MVP 범위](../product/mvp-scope.md) 13장 스파이크 1·3, [ADR 0001](../adr/0001-tech-stack.md) 8장에 답한다
- 상태: **완료.** 아래 결과로 ADR 8장과 MVP 범위 6.4.2를 수정했다

이 문서는 추측이 아니라 실제 파일을 열어 측정한 결과다.

## 1. 결론 먼저

| # | 발견 | 영향 |
|---|---|---|
| 1 | 패키지는 zip이지만 내용물이 **zstd 압축 + protobuf**다 | ADR의 "zip + SQLite" 가정이 틀렸다 |
| 2 | SQLite에 **`unicase` 커스텀 콜레이션**이 필요하다 | 등록하지 않으면 주요 쿼리가 실패한다 |
| 3 | 스키마 **ver 18**. 노트타입·덱이 정규화된 테이블이다 | 레거시 JSON 블롭 파싱이 필요 없다. 좋은 소식 |
| 4 | **Basic은 25%뿐**이다. 52%가 커스텀 노트타입 하나다 | **6.4.2의 노트타입 화이트리스트는 쓸 수 없다** |
| 5 | 그런데 템플릿은 전부 단순하다. JS·Cloze·type-in이 0이다 | 일반 지원이 화이트리스트보다 쉽고 커버리지도 100% |
| 6 | 노트 절반에 **`중요도::` 태그가 이미 붙어 있다** | 중요도 제안의 1순위 신호가 생겼다 |
| 7 | 카드 455장이 **필터 덱**에 임시로 올라가 있다 | `cards.did`만 읽으면 엉뚱한 덱에 들어간다 |
| 8 | revlog 7,745건이 온전히 들어 있다 | 복습 이력 이전이 기술적으로 가능하다 |

## 2. 패키지 구조

```text
itisyijy.colpkg (zip, 항목 231개)
├── meta                 2바이트. protobuf. 값은 version = 3
├── collection.anki21b   zstd → SQLite (901KB → 3.6MB, 4.1배)   ← 진짜 데이터
├── collection.anki2     SQLite 스텁 51KB. 구버전 Anki가 열었을 때 경고를 띄우기 위한 것
├── media                zstd → protobuf. 미디어 이름 매핑
└── 0 .. 226             zstd → 실제 미디어 바이트 (PNG 등)
```

매직 바이트로 확인했다.

| 항목 | 앞 4바이트 | 의미 |
|---|---|---|
| `collection.anki21b` | `28 b5 2f fd` | zstd |
| `collection.anki2` | `SQLite format 3` | 평문 SQLite (스텁) |
| `media` | `28 b5 2f fd` | zstd |
| `0`, `1`, ... | `28 b5 2f fd` | zstd. 풀면 PNG |

**주의할 점.** zip 자체는 `stored`(무압축)다. 압축은 zip 레이어가 아니라 각 항목 안에서 zstd로 되어 있다. zip만 풀고 SQLite로 열면 실패한다.

`collection.anki2` 스텁을 진짜 데이터로 착각하면 안 된다. 51KB짜리 빈 껍데기다.

### 필요한 라이브러리

| 용도 | Rust 크레이트 |
|---|---|
| zip 해제 | `zip` |
| zstd 해제 | `zstd` |
| SQLite | `rusqlite` |
| protobuf (`meta`, `media`) | `prost` 또는 수동 파싱 |

`meta`와 `media`는 protobuf지만 구조가 단순하다. `meta`는 2바이트(`08 03` = field 1, varint 3)이고, `media`는 이름과 인덱스의 반복이다. 전용 라이브러리 없이 수동 파싱도 가능하다.

## 3. `unicase` 콜레이션

`decks`와 `notetypes`의 이름 컬럼이 `unicase` 콜레이션을 쓴다. 등록하지 않고 쿼리하면 이렇게 실패한다.

```text
sqlite3.OperationalError: no such collation sequence: unicase
```

Anki가 런타임에 등록하는 커스텀 콜레이션이라 DB 파일 안에 정의가 없다. 파서가 직접 등록해야 한다.

읽기 전용 파싱에서는 **대소문자 무시 비교면 충분하다.** 정렬 결과가 Anki와 완벽히 같을 필요는 없다. 다만 데이터를 다시 쓸 일이 생기면 Anki의 구현과 맞춰야 한다.

rusqlite에서는 `create_collation`으로 등록한다.

## 4. 스키마 ver 18

정규화된 테이블 구조다. 구버전 Anki의 `col.models` / `col.decks` JSON 블롭이 아니다.

| 테이블 | 행 수 |
|---|---|
| `notes` | 4,694 |
| `cards` | 4,694 |
| `revlog` | 7,745 |
| `decks` | 140 |
| `notetypes` | 14 |
| `templates` | 16 |
| `fields` | 44 |
| `tags` | 793 |
| `graves` | 1,734 |
| `config` | 48 |
| `deck_config` | 1 |

노트타입의 필드와 템플릿이 각각 `fields`, `templates` 테이블로 분리되어 있다. **일반적인 노트타입 지원이 쉬워진다는 뜻이다.** 파싱할 JSON이 없다.

`decks` 컬럼은 `id, name, mtime_secs, usn, common, kind`다. `common`과 `kind`는 protobuf 블롭이고, 필터 덱 여부가 `kind`에 들어 있다.

덱 이름은 `\x1f`(unit separator)로 계층을 구분한다. 최대 깊이 3이었고, 인터뷰의 `과목 → 학습 단위 → 챕터` 구조와 일치한다.

## 5. 노트타입 분포 — 가장 중요한 발견

| 노트타입 | 노트 수 | 비율 | 템플릿 | 필드 |
|---|---|---|---|---|
| **빅분기 판별형** | 2,442 | **52%** | 1 | 6 |
| Basic | 1,181 | 25% | 1 | 2 |
| IS Basic (T/F + SA) | 402 | 9% | 1 | 2 |
| UXA Exam Card | 190 | 4% | 1 | 6 |
| STM Basic (styled) | 127 | 3% | 1 | 2 |
| ITPM Card | 126 | 3% | 1 | 4 |
| IT PM Q&A | 116 | 2% | 1 | 3 |
| IS Image (figure) | 12 | 0.3% | 1 | 3 |
| Basic (and reversed card) | **0** | 0% | 2 | 2 |
| Cloze | **0** | 0% | 1 | 2 |
| Basic (type in the answer) | 0 | 0% | 1 | 2 |
| Image Occlusion | 0 | 0% | 1 | 5 |

### 이게 왜 문제인가

MVP 범위 6.4.2는 지원 대상을 `Basic`, `Basic and Reversed`, `Cloze`로 적어놓았다. 그대로 구현하면 이 컬렉션에서 **4,694장 중 1,181장(25%)만 들어오고 3,513장이 "처리하지 못한 카드"가 된다.**

게다가 지원한다고 적어둔 `Reversed`와 `Cloze`는 **실제 사용량이 0이다.** 없는 것을 지원하려고 일하고, 있는 것을 버리는 구조다.

### 그런데 해결은 쉽다

사용 중인 노트타입 8개의 템플릿을 전부 검사했다.

| 기능 | 사용 |
|---|---|
| `<script>` (JavaScript) | **0** |
| `{{cloze:}}` | **0** |
| `{{type:}}` | **0** |
| `{{tts}}` | **0** |
| 조건부 `{{#field}}` | 2개 (ITPM Card, UXA Exam Card) |

전부 **필드를 치환하는 단순 템플릿**이다. 즉 노트타입을 이름으로 화이트리스트할 게 아니라, **필드와 템플릿을 일반적으로 처리하면 100%가 들어온다.**

스키마 ver 18이 필드와 템플릿을 테이블로 갖고 있으므로 일반 처리가 오히려 더 쉽다. 이름별 특수 처리를 짜는 것보다 코드가 적다.

조건부 `{{#field}}`는 두 곳에서만 쓰이고, "필드가 비어 있지 않으면 표시"라는 단순한 의미다. 이것까지 지원하면 사실상 전부 커버된다.

## 6. 중요도 태그가 이미 있다

노트 4,694장 중 **3,424장(73%)에 태그가 달려 있다.**

| 태그 | 노트 수 |
|---|---|
| `중요도::최우선` | 1,388 |
| `highlight` | 1,016 |
| `중요도::높음` | 940 |
| `unit_question` | 1,278 |
| `star3` / `star2` / `star1` / `star4` | 420 / 192 / 177 / 12 |
| `중요도::보통` | 114 |
| `과목::1` / `과목::2` / `과목::3` | 906 / 759 / 455 |

`중요도::` 3단계가 이미 존재하고, 우리가 설계한 `핵심 / 일반 / 보충`과 단계 수까지 같다.

### 다만 해석에 주의가 필요하다

**중요도 태그는 한 노트타입에만 붙어 있다.**

```text
중요도::* 합계 = 1,388 + 940 + 114 = 2,442
빅분기 판별형 노트 수        = 2,442
```

정확히 일치한다. `highlight`와 `star*`도 전부 같은 노트타입이다. 나머지 7개 노트타입에는 하나도 없다.

즉 이건 사용자가 태그를 도구로 활용한 결과가 아니라, **그 덱을 만든 LLM 생성 과정이 태그를 붙여준 것**이다. 인터뷰에서 *"태그는 솔직히 활용하는 방법을 몰라서 활용 못하고"* 라고 한 진술과 모순되지 않는다. 사용자가 만든 게 아니라 카드와 함께 딸려 온 것이다.

### 그래도 활용 가치가 크다

- 이 컬렉션의 **52%가 즉시, 추측 없이 중요도를 갖는다.**
- 덱 이름 키워드 추측보다 훨씬 정확하다.
- 사용자의 카드 생성 워크플로가 `자료 → LLM → 카드`이므로, 앞으로 만들 덱에도 비슷한 태그가 붙을 가능성이 높다.
- `highlight`와 `star*`는 원자료의 강조 표시에서 유래했을 가능성이 크다. 계획했던 [원자료 분석](../product/post-mvp-source-analysis.md)을 외부 LLM이 이미 일부 수행한 셈이다.

**그래서 중요도 신호의 우선순위를 이렇게 둔다.**

```text
1. 사용자가 직접 지정한 값       확정. 무엇도 덮어쓰지 않는다
2. 가져온 태그 (중요도::, star, highlight)
3. 하위 덱 이름 키워드
4. 없으면 일반
```

태그만으로는 48%가 남으므로 3번과 4번은 그대로 필요하다.

## 7. 필터 덱 함정

`Custom Study Session` 덱에 카드 455장이 들어 있다. 이건 실제 덱이 아니라 Anki의 **필터 덱**이고, 카드가 임시로 옮겨져 있는 상태다.

원래 덱은 `cards.odid`에 남아 있다.

```text
odid <> 0 인 카드: 455장

원래 덱:
  빅데이터분석기사::3과목 빅데이터 모델링::3-17 딥러닝 분석    33
  빅데이터분석기사::3과목 빅데이터 모델링::3-12 군집분석      33
  빅데이터분석기사::3과목 빅데이터 모델링::3-06 회귀분석      29
  ...
```

`cards.did`만 읽으면 **455장이 존재하지 않는 덱에 들어간다.** 게다가 중요도를 하위 덱 단위로 부여하기로 했으므로, 이 카드들은 중요도도 잘못 받게 된다.

**규칙: `odid`가 0이 아니면 `odid`를 실제 덱으로 쓴다.** 필터 덱 자체는 가져오지 않는다.

## 8. 복습 이력

| 항목 | 값 |
|---|---|
| revlog | 7,745건 |
| 신규 카드 (type 0) | 2,909 (62%) |
| 복습 카드 (type 2) | 1,698 |
| 학습 중 (type 1) | 84 |
| 재학습 (type 3) | 3 |

**복습 이력이 온전히 들어 있다.** 스파이크 3의 "이전 가능한가"에 대한 답은 기술적으로 "가능하다"다.

다만 `cards`의 `ivl`, `factor`, `due`, `reps`, `lapses`를 Addiem 스케줄러의 상태로 어떻게 매핑할지는 [ADR 7장의 SRS 경계](../adr/0001-tech-stack.md)가 정해진 뒤에야 답할 수 있다. 데이터가 있다는 것과 의미를 보존한다는 것은 다른 문제다.

62%가 아직 신규 카드라는 점도 참고할 만하다. 이 사용자는 덱을 다 돌지 못한 상태다.

## 9. 재현 방법

```python
import zipfile, zstandard, sqlite3

z = zipfile.ZipFile('itisyijy.colpkg')
raw = zstandard.ZstdDecompressor().stream_reader(z.open('collection.anki21b')).read()
open('collection.sqlite', 'wb').write(raw)

con = sqlite3.connect('collection.sqlite')
con.create_collation("unicase", lambda a, b: (a.lower() > b.lower()) - (a.lower() < b.lower()))
```

이 스파이크는 Python으로 실행했다. 구조 확인이 목적이라 언어는 상관없다. 실제 구현은 ADR 0001의 결정에 따라 Rust로 한다.

## 10. 남은 질문

| 질문 | 어디서 답하나 |
|---|---|
| `media` protobuf의 정확한 구조 | 구현 시점. 이름·인덱스 매핑이라 단순할 것으로 보인다 |
| `decks.kind` protobuf에서 필터 덱 판정 | `odid`로 우회 가능하므로 급하지 않다 |
| 구버전 `.apkg`(`collection.anki2` 본체)도 지원하는가 | 별도 샘플로 확인 필요. 이 파일에는 스텁만 있다 |
| Anki 스케줄 상태 → Addiem 매핑 | ADR 7장 확정 후 |

세 번째가 실질적으로 남은 유일한 위험이다. 오래된 덱을 공유받는 사용자는 구버전 포맷을 가져올 수 있다.
